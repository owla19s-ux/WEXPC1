# RDA-001：角色权限与 API / 模型选择

- 状态：草拟（核心场景已明确，部分验收仍需底层设计细化）
- 类型：跨模块端到端压力案例
- 来源：用户已确认的 WEXPC 产品方向；不是从 DSH 直接复制的架构。

## 1. 需求事实

- WEX 有主 AI、秘书／管家、执行 AI、审查 AI 等职责角色；角色与岗位可分离，同一 AI 可以承担不同岗位。
- 秘书／管家在用户授权范围内可拥有较高自主权，能主动选择和调用获准的模型与能力。
- 普通施工 AI 的权限应较低，并受到施工任务、资源范围和施工卡约束。
- 角色不是单纯的人设标签；职责、自主范围和执行权限必须能进入系统决策。
- API 接入需要支持多 Provider、多模型和凭证管理；模型选择不能自动授予工具、文件、仓库或终端权限。
- 系统既不能把所有工作流锁死为预定义步骤，也不能允许 AI 通过自然语言声明或角色名扩大权限。

## 2. 场景

### 场景 A：秘书自主选择模型

用户允许秘书在指定 Provider、预算、隐私和可用模型范围内选择模型。秘书可按任务性质选择模型，并调用自己获准使用的工具完成多步工作。

### 场景 B：施工 AI 执行受限任务

调度器把任务卡分配给施工 AI。任务卡限定目标、资源范围、允许的能力、接口约束和验收要求。施工 AI 可以在授权范围内自行安排实现步骤，但不能擅自扩大任务或资源范围。

### 场景 C：模型切换与审查

同一职责角色可因任务切换模型；主 AI 可让一个模型执行、另一个模型审查。模型切换不得改变执行主体身份、任务权限或操作回执的关联关系。

### 场景 D：越权与策略冲突

角色策略允许某类操作，但全局访问开关关闭、目标资源未授权或强制安全规则拒绝。系统必须拒绝操作，并提供可解释、可审计的结果；角色级高权限不能覆盖这些边界。

## 3. 涉及的概念（待映射到底层模块）

- Role / Duty：职责身份。
- Agent / Participant：执行主体及其实例。
- Task / Work Card：任务目标、范围与验收条件。
- Provider / Connection：模型服务连接。
- Model / Capability Metadata：模型标识与能力描述。
- Credential：凭证本体及使用授权。
- Tool / Capability：可调用操作能力。
- Resource Scope：项目、Space、目录、仓库、终端等资源边界。
- Policy / Grant / Approval：策略、授权来源与审批。
- Operation / Receipt / Audit Record：操作状态、执行结果与审计事实。

这些概念必须在设计中保持语义区分，但不预设它们都要成为独立服务、模块或持久化实体。

## 4. 端到端预期链路

1. 用户配置角色职责、允许的自主范围及相关授权。
2. 调度器创建或选择任务，并确定任务范围与验收要求。
3. 运行时根据角色、任务、可用 Provider/Model 和策略解析本次模型调用配置。
4. 连接层在不向模型暴露不必要凭证的前提下完成调用。
5. 模型返回文本或工具调用提议；提议本身不等于授权。
6. 统一执行边界结合主体、任务、资源、动作和策略作出允许、询问或拒绝决定。
7. 获准后由对应连接器／执行器实施操作，记录副作用、错误和结果。
8. 调度器依据真实回执决定继续、重试、换模型、升级审批或结束任务。
9. 最终结果回到对应对话与任务，并保留可追踪的调用、操作和验证记录。

以上是用于压测的预期语义链，不是已确定的最终模块调用顺序。

## 5. 必须通过的架构检查

### 身份与配置

- 角色职责、模型选择策略、Provider 连接、Credential 使用权和工具权限可分别配置。
- Role 不与单一模型或 API Key 永久绑定。
- 模型切换不创建隐式新身份，也不扩大既有权限。

### 权限与自主性

- 高自主角色可以在授权范围内连续执行多步操作，不需要为每一步都强制询问用户。
- 低权限施工 AI 的任务范围和资源授权不能由它自身修改或扩大。
- 全局禁用、资源授权缺失和不可覆盖的强制拒绝不能被角色策略、插件顺序或模型输出覆盖。
- Prompt、系统提示词或角色名称不能单独作为授权凭证。
- 模型可见的工具列表与真实执行时的授权检查保持一致；最终执行边界不能只依赖 UI 隐藏按钮或模型自律。

### 并发与生命周期

- 并行任务不会意外共享或继承其他任务的授权范围。
- 每次调用可关联到角色实例、任务、模型路由和相关操作回执。
- 取消、超时、重试和切换模型不会导致同一副作用被不受控地重复执行。
- 任务结束或角色停用后，不能继续发起新的未授权操作；在途操作的处理规则必须明确。

### 结果与审计

- 记录实际使用的 Provider/Model、策略决定、执行结果和相关验证状态；秘密凭证不得写入普通日志。
- 将模型提议、授权决定、操作执行、最终回执分成不同事实。
- 只有真实执行和验收证据满足条件，施工卡才能标记为完成。

## 6. 故障与反例测试

1. 秘书选择了有效模型，但该角色没有使用对应凭证的权限。
2. 施工 AI 请求读取施工卡范围外的目录。
3. 角色策略允许调用，但全局访问开关关闭。
4. 模型返回一个未注册或已停用的工具调用。
5. Provider 超时后，操作结果未知；调度器尝试换模型重做。
6. 两个并行任务使用相同角色模板，但各自拥有不同资源授权。
7. 审查 AI 可以读取变更和测试证据，但不应自动继承施工 AI 的写权限。
8. 用户撤销连接或资源授权时，系统正有在途调用。
9. 某个扩展试图通过更换策略插件或注册顺序覆盖强制拒绝。

每个测试都必须明确预期状态、允许发生的副作用、拒绝原因与回执内容；具体测试契约待底层协议设计阶段补齐。

## 7. 架构缺口判定方法

若案例失败，先定位缺口类型，不直接重写整个架构：

- 对象模型缺口：角色、主体、任务、凭证或资源范围无法被准确表达。
- 契约缺口：模块没有提供必要的公开操作或查询能力。
- 协议缺口：调用、取消、错误、重试或回执语义不完整。
- 策略缺口：授权来源、决策顺序或强制拒绝规则不明确。
- 运行时缺口：并发隔离、动态替换、停用和恢复不能兑现契约。
- 验证缺口：无法用自动化检查或可复现测试证明行为正确。

只有证据表明现有抽象无法满足多个已确认需求时，才扩大架构修改范围。

## 8. 待决问题

- 角色、岗位、Agent 实例之间的最终数据模型与继承规则。
- 秘书可自主选择模型的具体范围、预算约束与隐私限制如何配置。
- 角色授权、任务授权、资源授权与用户审批的优先级和组合规则。
- Credential 的具体存储、引用、轮换与撤销机制。
- 模型调用与工具操作的持久化粒度，以及未知结果的恢复协议。
- 审查 AI 的只读证据访问范围和与施工 AI 的隔离机制。

这些问题未解决前，不得把示例当作最终权限模型。
