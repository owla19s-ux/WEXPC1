# 需求对冲架构（Requirement-Driven Architecture Stress Tests）

- 状态：需求案例库；用于检验候选架构，不等于正式架构决策。
- 目的：把 WEX 的复杂真实需求转成可重复执行的架构压力测试，提前暴露对象模型、模块边界、协议、权限和运行时设计的缺口。
- 使用原则：案例先记录需求与验收，不预设实现；只有通过案例验证的设计结论，才可进入正式底层规范。

## 使用方法

每个案例都按同一结构编写：

1. **需求事实**：已确认的用户行为与目标。
2. **场景与参与对象**：角色、Agent、任务、Space/Context、连接、模型、凭证、工具、资源等。
3. **端到端流程**：从用户意图到执行结果和回执。
4. **架构压力点**：可能暴露缺口的对象、接口、协议、依赖、状态所有权或生命周期。
5. **边界与失败场景**：越权、并发、断线、超时、重试、切换、崩溃与恢复。
6. **可验证验收条件**：可执行测试、架构检查或可复现证据。
7. **待决问题**：未确认的产品语义与候选方案，禁止擅自补全。
8. **设计影响记录**：关联的模块契约、规范、施工卡及决策状态。

## 案例状态定义

- **草拟**：场景已记录，但存在关键语义缺口。
- **可压测**：场景、边界和验收条件足够具体，可以用于审查候选设计。
- **验证中**：正在用接口设计、原型或自动化测试验证。
- **通过**：指定架构版本满足该案例的全部验收条件；必须附证据。
- **失败**：出现明确反例，需修订设计或记录接受的限制。
- **废弃**：需求被用户撤回或被更新需求替代，保留历史原因。

## 规则

- 案例库与 DSH 源码研究资料分开：前者定义 WEX 要实现什么，后者研究可借鉴的实现机制。
- 案例通过不代表整个架构通过；需要覆盖多个案例及模块间交互。
- 不允许把“文档写了”“AI 认为可以”作为通过证据。
- 不允许因某种语言或框架实现困难就擅自降低已确认的产品需求；应先评估替代运行时与技术组合。
- 案例本身不自动授权代码修改，也不自动冻结架构。

## 后续扩展

后续按真实复杂需求增加案例，例如：可插拔模块运行时加载、连接器组合、任务调度与回执、跨 Space 的上下文边界、扩展卸载与在途任务、AI 施工卡生成与验证。只有当需求在项目中已确认或用户明确提出时，才将其登记为正式案例。
