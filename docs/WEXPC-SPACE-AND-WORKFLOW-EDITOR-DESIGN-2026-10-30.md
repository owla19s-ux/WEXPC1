# WEXPC Space 组织、目录接入与工作流编辑器共识（2026-10-30）

> 状态：本轮用户确认的**产品组织与技术首选**；不是已实现功能、冻结的数据协议或 WEXPC 主仓版本变更。
> 范围：Space 页面组织层次；Space 工作区与独立 Context 目录；人和 AI 共编工作流；React Flow 选型；任务卡和调度器在流程中的关系。
> 当前阶段：个人自用和开发优先；不为可能的公司/公开发行场景提前开发跨组织存储、云端权限和协作平台。

## 1. 空间组织：管理层级和实际工作内容分开

可见组织结构：

```text
WEX Space 页面（入口）
└── 空间类别：个人 / 工作 / 公开 / 公司等
    └── Space 工作区（一个类别下可登记多个；各自选择所在磁盘与目录）
        └── Group（可选逻辑分组）
            └── Context（真正使用 AI、工具、资料、对话、工作流的工作环境）
```

- **空间类别**：当前仅承担逻辑组织、入口和展示；不绑定物理目录。个人/工作/公开/公司体现空间性质，不是“开发/小说/研究”的内容模板。未来确有跨组织、跨项目等大规模需求时，才研究类别级存储、共享与权限业务。
- **Space 工作区**：可以在 D/E/F 等不同磁盘创建或绑定真实目录；用来聚合、管理 Context，也可以有自身元信息。
- **Group**：可选分组，先作为逻辑整理层，不强制对应真实文件夹。
- **Context**：实际工作与资料关系的承载点。按需关联 AI、连接器、外部文件目录、工具、任务、流程与对话。不是所有引用的实体都必须复制到 Context 文件夹里。
- 层级是**界面与管理关系**，不是每次创建 Context 必须走过的强制向导，也不要求磁盘目录逐级一一嵌套。
- Space 页负责组织和目录关联，不重复实现 AI 调用、工具执行、工作流运行等功能；普通聊天依然可独立使用。

## 2. 两种平等的目录入口

### A. 创建或绑定 Space 工作区
用户主动指定一个实际目录，例如 `D:\Projects\WEX\`。这个目录作为该工作区的文件入口，可以保存工作区配置，以及由其管理的 Context 的元信息、对话、工作流及自有资料（具体子目录名暂不冻结）。

### B. 直接创建或添加独立 Context 目录
用户可直接选择 `E:\Research\AI\`，无需先创建 Space 工作区；以后可以将它关联到 Space 或 Group。**关联不等于移动、复制、删除文件**。

两种入口调用同一套 Context 能力，不建立两种不同的 Context 系统。

实际文件位置与 WEX 组织关系分离：
- 不同工作区可以在不同磁盘，同一类别下不需要统一父目录。
- Context 引用某个外部项目目录、Git 仓库或资料地址时，保存引用关系即可；不自动搬迁实际资源。
- 用户明确指定输出位置时按指定位置写入；未指定时可按当前工作区/Context 的数据目录策略保存 WEX 产生的资料，具体默认规则后续细化。
- WEX 安装目录、WEX 公共数据目录、用户选择的工作区目录和独立 Context 目录是**不同概念**；可以同盘也可以异盘。公共数据目录保留连接配置、AI 公共配置、登记索引及必要应用状态等，不应强制吸纳所有 Space/Context 的实际资料。
- 关闭 WEX 后，其他有正常文件权限的本地 Agent 可直接读取相关文件；不额外建设“离线诊断平台”。源码、部署文件、日志应可定位对应关系，但不强制所有内置模块独立编译或一一物理映射。
- 工作区/Context 的重命名、重名、移动后的重新定位、关联与删除行为待具体化；不能因为简单改变组织类别就隐式移动磁盘资料。

## 3. 工作流：首先解决“用什么编辑”，再研究调度

用户期望：在画布上拖动节点、画路线、把 AI/工具/人工步骤配置到节点；用户和 AI **同时围绕同一份工作流定义**持续编辑，画布直接反映双方的变更。

### 3.1 技术选型

- **首选：React Flow（`@xyflow/react`）**，用于 React/Tauri 桌面端的节点、连线、自定义节点、缩放拖拽、布局及可视编辑。
- **备选：Rete.js**；不并行建设两套编辑器。
- React Flow 是**画布组件而非任务调度器、工作流业务协议或现成多 AI 执行平台**。选型首选已确认，尚未在 WEXPC 中进行安装、编译、桌面集成及原型验证。
- 参考：[React Flow](https://reactflow.dev/)；[保存/恢复示例](https://reactflow.dev/examples/interaction/save-and-restore)；[连接校验示例](https://reactflow.dev/examples/interaction/validation)；[Rete.js](https://retejs.org/)。
- React Flow 的具体包版本和组件 API 应在原型开始时按官方最新文档确认；不要从历史教程照搬旧包名。

### 3.2 用户与 AI 共同编辑

- 用户可手动添加、移动、删除节点，连接/断开路线，选择 AI、工具、条件与参数。
- AI 可在用户允许的范围内，通过**结构化编辑操作**添加/修改/删除节点、连线、配置及布局；**不通过模拟鼠标，也不能直接覆盖整份流程文件**。
- 手动操作与 AI 操作进入同一工作流编辑入口，修改同一份正式定义，画布同步显示。
- 支持可撤销/重做、变更记录；批量或破坏性编辑允许预览与确认。具体授权边界遵循 WEX 现有权限原则，不新造单独的 AI 编辑权限平台。
- 区分**流程的业务定义**（节点类型、连接条件、绑定 AI/工具及输入输出）和**画布布局**（位置、缩放等 UI 属性），避免把 React Flow 的视图快照当作完整业务协议。
- 人与 AI 可以交替或并行提出修改，但需要防止版本覆盖和冲突；前期不需要引入 Yjs 式联网多人实时协作体系。

## 4. 工作流、任务卡、调度器的关系（仅确认概念，运行细节后研）

一个流程可以处理**几百张任务卡**，不能把每一张任务卡画成一个工作流节点。

```text
工作流定义：任务池 → 任务分配 → AI 执行 → AI 审查 → 结果判断
                                                 ├── 通过 → 后续流程/完成
                                                 ├── 返工 → 原执行节点
                                                 ├── 重派 → 任务池重新分配
                                                 └── 异常/不明 → 等待核实或人工处理
```

- **画布**定义任务流转路线、节点及条件；**任务卡**记录单项工作的描述、状态、关联产物、审查与尝试记录；**调度器**负责依据流程分派、等待、交接和推进；**AI/工具**执行具体工作和审查。不得由画布组件负责实际执行。
- 调度器是整体运行机制，**不必在每段连线上添加一个“调度器节点”**。可将任务分配、执行/审查及条件转移表现为可配置节点。
- 初期建议的节点类别：任务入口/任务池、执行（AI/工具）、审查、条件判断、人工介入。此为**原型候选**，非冻结节点契约；重复任务、循环、限额、失败退回等更复杂语义待后续设计。
- 审查不通过、调用工具失败、操作结果未知是不同事实；不能一律盲重试。真实测试产物和 AI 口头宣称也不能混淆。
- 建议将编辑视图（结构/配置）与运行视图（等待、处理、阻塞、返工的任务卡数与详情）分开，同一份任务事实，不复制任务状态。
- 修改正在运行的工作流如何生效、版本如何保持、任务并发及冲突如何解决，**留到调度器研究**；不得因选画布库擅自冻结复杂执行协议。

## 5. 首个受限验证：先验证编辑，不提前做运行引擎

1. 在 WEXPC React/Tauri 环境验证 React Flow 集成。
2. 用户创建任务入口、AI 执行、审查与条件节点，连出通过/返工/重派路线。
3. 用户通过对话让 AI 添加审查节点或修改连线，实际走统一编辑 API，画布同步变化；可先用明确结构化操作模拟 AI 指令，待界面能力通过再接模型。
4. 用户继续手动编辑；验证撤销、无效连接校验和编辑冲突的最小处理。
5. 将流程定义与布局保存到**用户选定的 Context/工作区**，关闭并重新打开后恢复。
6. 不接真实的几百任务派发、多 AI 并发、审查自动返工；这些是下一阶段调度器验证范围。

## 6. 当前决策边界与文档优先关系

- **已确定**：Space 类别当前无物理地址；Space 工作区和独立 Context 均可由用户自主选择目录；组织关系不要求移动文件；人和 AI 共编同一工作流；React Flow 为工作流编辑器技术首选。
- **仍待研究**：子目录与配置格式、实际文件持久化、重名及移动规则、完整节点语义、工作流运行与调度、在途编辑及 Tauri 实际集成表现。
- **没有批准**：自动调整 0.1.1/0.1.2 版本范围、迁移 WEXPC 代码、现在做复杂组织/企业共享存储、宣称运行验证通过。
