# WEXPC1 底层架构压力测试任务书

状态：研究任务书；不改变现有架构决策、产品范围或版本基线。
日期：2026-10-28

## 一、任务目标

对 WEXPC1 当前架构开展需求驱动的系统性压力测试。

核心问题不是“架构看起来是否完整”，而是：

**能否根据架构文档、底层契约和模块规范，形成明确的施工任务，使不同 AI 能独立实现不同模块，最后通过稳定接口组合运行，而不依赖临场猜测和大量跨模块修补？**

当前阶段只做研究、需求对冲、架构细化和技术可行性验证，不确定版本计划，不擅自开始大规模代码施工。

## 二、资料与证据规则

1. 阅读 WEXPC1 当前架构文档、底层设计、需求对冲案例、DSH 参考和 Hermes Agent 参考。
2. 结合 DSH、Hermes Agent、SkillHub 的真实源码、协议和插件实现。
3. 不将产品宣传、文档描述、静态源码阅读和实际运行验证混为一谈。
4. 所有发现标注来源、证据等级、当前状态及尚未验证的假设。
5. 原始设计文档一律只读。所有分析、修订建议、对照表和新方案写入独立文件。

## 三、必须对冲的复杂需求

### A. 角色与 Agent
- 主 AI、秘书、执行 AI、审查 AI 等岗位可复任，不将角色、岗位、Agent、模型和权限绑定。
- 不同角色具有不同授权范围；秘书可以拥有较高的用户授权，但不能仅凭角色名称自动提权。
- 子 Agent 可以跨任务持续工作、被取消、恢复和更换模型。
- 角色记忆保留自身经验，并可选择向公共策略库贡献经过筛选的经验。

### B. Space、Context 与公共策略库
- Space、Group、Context 的共享、继承、隔离和引用。
- 个人、工作、公开、公司等归属类别及不同权限级别。
- 角色记忆、项目 Context、Session、Task、公共策略库分别拥有明确的数据所有权。
- 公共策略库记录事件、分析、判断、行动结果和策略修订，支持相互矛盾的策略并存、来源追溯、验证和撤回。
- 公共知识更新不应无条件改变正在运行的 Agent 上下文。

### C. 插件、能力与运行时
- DSH 式能力注册、模块组合、生命周期管理和热插拔。
- Hermes 式技能、记忆提供者、子 Agent、定时任务与多入口协作。
- Skill、宿主插件、连接器、模型 Provider、Memory Provider 和 UI 扩展具有不同的权限及生命周期。
- 新增扩展后可以在不关闭宿主的情况下重新加载相关 UI；区分文件热加载、配置热更新、插件激活和原生代码热替换。
- 能力市场支持来源、版本、依赖、兼容性、权限声明、升级、停用和恢复。

### D. 外部连接与生态
- 社交平台、学习网站、浏览器、GitHub、模型 API 和外部 Agent 客户端。
- 一项连接可提供多种能力；连接身份、外部账号、能力身份、资源身份和操作身份相互区分。
- 外部服务断线、撤权、限流、部分成功、结果未知时，状态与回执仍可信。

### E. 用户体系与自建云空间
- 用户、账号、设备、客户端安装实例、组织、项目和资源分别具有稳定身份。
- 本地与云端存储可替换；资源具有版本、归属、共享、撤权和迁移语义。
- 公开项目不自动公开私人记忆、凭证或内部资源。
- 账号系统不可用时，本地功能和已有资源不应被不必要地破坏。
- 预留未来多用户、公司、组织及其他控制域的扩展能力，但不提前实现完整复杂安全体系。

### F. 持续任务与 AI 施工
- 调度器、任务、执行操作、操作回执和工作流状态各有明确 owner。
- 支持并发 AI 分工、冲突检测、审查、修订、验证和恢复。
- AI 能根据模块契约和施工规范形成施工卡，而不是猜测接口。
- 任务完成、代码提交、测试通过、合并和正式交付必须有明确区别。

## 四、必须产出的结果

1. **需求—架构对冲矩阵**：每个案例能否被现有架构表达，缺失什么，证据是什么。
2. **对象与身份模型**：角色、岗位、Agent、用户、账号、设备、Space、Context、Session、Task、Operation、Capability、Connection、Resource 等对象的关系与所有权。
3. **模块与依赖契约**：目录结构、模块职责、公开接口、依赖方向、机器可读清单和禁止依赖规则。
4. **协议与生命周期规范**：注册、激活、调用、授权、取消、停用、更新、失败恢复和版本兼容。
5. **数据与状态所有权表**：谁是权威状态持有者，哪些只是投影、缓存或引用。
6. **施工卡生成规则**：如何从已确认契约中生成任务、约束、修改范围、测试要求和验收条件。
7. **验证计划**：区分静态审计、契约测试、最小原型、故障注入和目标平台运行验证。
8. **未决问题清单**：明确哪些必须由用户决定，哪些属于技术研究，不要把所有问题都推回用户。
9. **外部参考索引**：将 DSH、Hermes、SkillHub 的可借鉴机制与不应照搬的部分逐项映射。

## 五、架构验收标准

每个核心模块至少应明确：
- 模块身份与职责；
- 输入、输出和错误语义；
- 公开接口与允许依赖；
- 权限与信任边界；
- 状态所有权与持久化规则；
- 生命周期与并发行为；
- 失败、取消和恢复行为；
- 可独立执行的测试；
- 变更对其他模块的影响范围。

至少选取一个插件热插拔链路、一个跨角色记忆共享链路、一个跨 Context 授权链路和一个长期任务恢复链路进行端到端验证。

如果现有语言或运行时无法满足要求，提出可比较的替代方案及迁移成本，不预设必须更换语言。

## 六、组合故障压力测试

必须至少分析以下并发场景：

秘书正在执行任务时，用户撤销了它对某个 Space 的权限；另一个 Agent 同时更新公共策略库；被委派的子 Agent 正在调用一个准备热更新的插件；主任务随后崩溃并恢复。

系统必须明确：
- 哪些调用立即被拒绝；
- 哪些已开始的外部副作用结果未知；
- 哪个策略版本对当前执行有效；
- 插件何时允许卸载；
- 恢复后如何防止意外重复执行；
- 回执与审计记录如何保持可信。

不能只分别证明角色、记忆和插件机制成立，必须检验它们交叉时的状态所有权和生命周期。

## 七、工作顺序与保护规则

需求对冲 → 架构修正建议 → 底层契约 → 技术可行性验证 → 施工规范 → 最后才确定版本计划。

- 不修改原文档，不自动改变现有版本基线。
- 不以新增文档数量代替验证。
- 不在没有证据时宣布架构已经通过。
- 不因个别案例不匹配就推翻整体架构；先定位具体缺口。
- 不把 DSH、Hermes 或 SkillHub 的机制直接照搬为 WEX 规范。
- 如果现有语言或运行时无法满足要求，比较替代方案和迁移成本，而非预设必须换语言。

## 八、最终验收问题

**如果把这套规范交给另一个 AI，它是否能够在不反复询问架构意图、不随意修改其他模块的前提下，独立完成一个功能模块，并通过明确的契约和测试接入整个 WEX？**

如果不能，指出具体缺口并继续细化，而不是用“未来可以扩展”作为结论。
