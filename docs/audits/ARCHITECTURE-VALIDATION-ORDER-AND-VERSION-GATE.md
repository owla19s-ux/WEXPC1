# WEXPC 架构验证顺序与版本规划门槛

状态：工作流程原则 / 待纳入正式协作规范；不修改既有设计文档或当前版本基线。
日期：2026-10-28

## 核心原则

先用真实需求对冲架构，再补齐底层设计并验证，最后才确定版本计划。版本规划不得反向限制尚未验证的架构探索，也不能把候选设计自动当作产品承诺。

## 固定工作顺序

1. **需求对冲**：收集真实复杂案例，明确参与主体、上下文、权限、生命周期、失败条件与预期结果；标注已确认、候选、假设和长期研究。
2. **架构检查与修正**：逐案例检查现有架构能否表达；识别职责冲突、状态所有权不明、接口缺失和不可扩展点。新分析写入独立文档，不覆盖原文。
3. **底层设计**：定义目录/模块边界、机器可读清单、接口协议、稳定标识、依赖规则、状态转换、错误语义、生命周期与回执。
4. **最小技术验证**：通过可运行原型或明确可重复的测试，验证关键设计假设；静态阅读、文档描述、编译通过、运行验证必须分别标注。
5. **施工规范闭环**：将已验证约束转成机器检查、模块施工要求、施工卡模板和验收条件，检查是否能独立施工而不产生跨模块缝合。
6. **版本规划**：前述阶段有足够证据后，再按价值、风险、依赖和成本划分版本；未经用户确认不自动改变现有版本范围。

## 每个需求案例的最小记录

- 案例 ID、来源和状态
- 参与主体 / Agent / 岗位 / 设备 / 外部服务
- Space / Group / Context / Session / Task 等对象关系
- 所需能力、授权来源与边界
- 正常路径、失败路径、取消与恢复
- 数据持久化与可信回执要求
- 当前架构是否可表达、证据和缺口
- 对底层契约的影响
- 是否需要原型验证
- 版本影响：暂不评估，直到架构与验证阶段完成

## 验证门槛

不得仅因“文档已写”判定设计通过。至少区分：
- 静态源码/文档检查
- 类型或契约测试
- 可运行原型验证
- 故障与恢复验证
- 目标平台验收

对于尚未具备本机 Windows 环境的情况，明确记录验证限制，不虚报 Windows 运行成功。

## 文档保护与变更追溯

- 原设计文档保持只读；审计、修订方案和整合结论写入新文件。
- 发生冲突时记录差异和建议，等待明确的架构确认，不以新文档悄悄替换旧设计。
- DSH、Hermes 等外部项目只提供参考机制，不自动成为 WEX 规范。
- 需求案例通过后，仍需确认其对正式架构的影响；不得由单个案例直接推导整个产品范围。
- 版本计划是最后的规划产物，不是架构探索的前置约束。

## 当前定位
