# 基础能力完整性审查与能力组合矩阵（2026-10-31）

审查基线：`owla19s-ux/WEXPC1@d00c15c3c1242a53e15c9d4719a3ce2fb966b803`

性质：施工安排前的基础能力盘点。只检查“基本功能是否齐全、能否组合”，不重新设计复杂业务平台、不批准新产品范围、不冻结实现接口、不制定施工批次。本报告不修改任何模块契约、架构决策或施工计划。

## 1. 本轮审查采用的简单原则

**基础能力是可以被独立调用、具有明确输入/输出和责任归属的基本动作；复杂功能是这些动作按场景组合后的结果。**

例如：
- “调用模型”是基础能力；“多 Agent 软件开发团队”是组合功能。
- “读取文件”是基础能力；“软件开发模板读取仓库、分析代码并分配任务”是组合功能。
- “保存、检索、关联资料”是基础能力；“角色长期记忆、项目知识库、公共策略库”是不同的组合应用。
- “创建节点、连接输入输出、执行一步”是基础能力；“软件开发工作流”是组合功能。

因此：
1. 基础能力不等于独立顶层模块；优先归入现有 owner。
2. 一个基础能力可被多个模块组合使用，但不因此建立全局万能服务。
3. 先满足真实使用需要，不为尚未出现的消费者建设抽象平台。
4. UI、配置、数据、权限和执行可以由不同模块负责，但用户完成一个基本动作时不能出现断链。
5. 参考项目只用于发现基本动作，不直接继承其复杂框架。

## 3. 基础能力完整性矩阵

- **已有实现**：当前产品源码中有对应实现；只代表列出的范围。
- **实验/原型**：有可运行实验，但尚非产品能力。
- **已设计未实现**：职责或契约已有描述，尚无产品代码。
- **边界未明确**：资料提到该能力，但最小行为或归属尚未收敛。
- **范围待确认**：存在不同文档描述，不在本轮擅自决定版本归属。

## 4. 目前最值得补清楚的基础缺口

以下是本轮确认需要继续收敛的事项。它们不等于新增模块，也不等于全部进入首版。

### G1. 资源引用与附件的最小用法

当前有 Space 的资源关联、local 文件访问、Task 产物引用等分散设计，但缺少足够明确的最小共用语义。

需要能表达：
- 资源来自哪里（本地文件、目录、仓库、远端对象、会话附件等）。
- 本次引用指向什么对象/位置。
- 使用时需要读取什么内容或元数据。
- 资源是否变化，以及依据是否过期。
- 资源在会话、Task、Context 中是“引用”还是“复制附件”。

不建议建立万能 Resource Center 或集中接管文件。来源仍归原系统；使用方只持有受控引用。

### G2. 原生 API 的最小工具往返

当前已经明确模型输出工具意图不等于执行，但没有明确最小循环由谁负责。

最低只需要解决：
1. 请求模型。
2. 收到普通内容或工具意图。
3. 工具意图进入 permissions 与 connections 受控边界。
4. 收到工具结果。
5. 将结果关联回本轮模型上下文。
6. 决定继续请求模型或结束。

这不要求先建设自主规划、长期记忆、子 Agent 池或完整 Agent Runtime。外部 DSH 的循环仍由 DSH 自己负责。

### G3. 非对话入口的基本权限

当前权限代码只对 conversation 入口有完整允许路径。Task、本地工具、受控回调等入口仍返回策略未解决。

这不是要求一次设计复杂权限平台；只需明确每种真实入口如何提供可信主体、目标和动作，以及默认拒绝/需批准的基本结果。

### G4. 调用结果、进度与取消的最小反馈

连接器可以有不同能力，但用户至少需要知道：
- 请求是否已发出。
- 当前是否仍在等待或运行。
- 是否取得部分结果。
- 是否成功、失败或结果未知。
- 取消是请求中、已确认，还是无法确认。
- 是否可以安全查询或重试。

不需要强行统一所有厂商状态机，也不需要引入消息总线。

### G5. 内部检索与互联网搜索分开

- 外部 Search/Fetch：连接器提供互联网搜索与网页抓取。
- 内部检索：定位自己的 Space、Context、对话、文件引用、Task 和结果。

两者的目标、权限和数据来源不同。先明确最小检索入口，不必立即做全文搜索集群或复杂向量数据库。

### G6. 配置、凭证、日志的基本闭环

目前有基础存储，但没有真正完成：
- 各模块配置保存和版本兼容。
- 系统凭证安全保存与引用。
- 可查询的持久化日志/诊断。
- 用户可见的错误定位和脱敏导出。

这些是桌面应用正常使用和排错所需的基本设施，不应被误认为已有实现。

### G7. 输入与附件体验

除了文本，还需明确最小文件选择/拖入/粘贴、附件预览、来源引用和权限检查。语音输入、复杂富文本编辑不因此自动成为首期必需。

## 5. 哪些复杂能力暂时不要建设

为避免重新把简单事情做复杂，本轮明确不建议把以下内容作为基础能力的前置：

| 暂不作为前置 | 当前只需要保留的简单基础 |
|---|---|
| 完整自主 Agent / Agent Loop 平台 | 普通模型调用与必要的工具往返；外部 Agent 自己管理内部循环 |
| 通用事件总线 / 消息中间件 | 直接调用、窄通知、按需查询最新状态 |
| 万能资源管理器 | 稳定资源引用、来源定位、按需读取 |
| 全量知识图谱 / 公共记忆平台 | 基本保存、查询、关联和来源记录 |
| 完整插件市场 / 动态热更新平台 | 内置模块装配；DSH 插件兼容独立演进 |
| Cron / 复杂自动化调度中心 | 手动触发和异步结果查询；未来有明确场景再加定时触发 |
| 全局业务数据库管理器 | 各领域拥有自己的数据与迁移，shared 提供技术原语 |
| 全连接器统一能力集合 | 每个连接器声明实际支持的能力，不支持就明确返回 |
| 多视图/三维/跨图传播引擎 | 先让单一基本视图可靠编辑和呈现真实对象 |
| 账号体系、云端同步、市场 | 保持个人本地使用目标，不作为基础设施前置 |

## 6. 用三个简单组合检查基础能力是否够用

这些只是组合检查样本，不是施工链路或新增模块。

### 样本 A：普通对话使用本地工具

用户输入 → 选择模型 → 模型输出工具意图 → 权限判定 → 调用本地文件能力 → 返回结果 → 模型继续生成 → 保存消息。

检查点：不需要先建 Space、Task、Workflow 或多 Agent 团队；工具结果能回到同一轮对话；拒绝时没有实际副作用。

### 样本 B：工作流组合 API、文件和外部 Agent

创建步骤 → 配置输入输出 → 连接步骤 → 校验 → 手动运行 → 调用不同连接器 → 查看每步结果。

检查点：工作流只组合能力；连接器不负责 Task；画布不拥有业务状态；任何一步都能说明输入、输出和失败。

### 样本 C：资料在多个功能中复用

选择一个本地文件 → 关联到 Context → 在对话中引用 → 作为 Task 输入 → 生成产物引用 → 重新打开时核对文件是否变化。

检查点：文件不被无意复制；引用可定位；不同入口重新检查权限；来源变化后旧结果不会冒充最新。

## 7. 本轮结论

1. **没有证据要求推翻现有一级模块划分。** 当前模块基本能够承接这些基础能力，主要缺口在少数基础行为的归属和跨模块组合边界。
2. **当前最重要的遗漏不是更多复杂模块，而是基本动作的闭环。** 资源引用/附件、原生 API 工具往返、非对话权限、调用进度/结果、内部检索、配置/凭证/日志需要优先补清楚。
3. **Search/Fetch 的版本归属存在文档冲突。** 子目录写首版，功能全景写长期；本轮只登记冲突，不代替用户决定版本。
4. **基础模块已实现不代表整个基础设施齐全。** shared、permissions、app 的现有代码是窄基础，不是完整产品底座。
