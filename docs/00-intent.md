# 00 — 设计意图与判断标准

> 本文只回答“为什么”，不回答“具体怎么建”。具体目录见 01，编码规范见 02。

## 1. 从口述中提炼的六个意图

### 1.1 功能模块是维护单位，不是技术层

给 GitHub 增加一个功能，理想情况是只改 GitHub 模块内部的代码、能力声明、测试和说明，而不是同时改“网络模块、认证模块、工具注册模块、请求分发模块、业务服务、响应处理、权限适配”。

这意味着：**代码归属的第一判据是“这个功能完整地属于谁”，而不是“这段代码在技术上属于哪一层”。**

### 1.2 公共机制只做共性，不吞业务

公共机制负责所有模块都必须一致的东西：凭证怎么存、权限怎么组合、操作怎么记账、回执怎么表达、事件怎么发、状态怎么持久化。

公共机制**不负责**：GitHub 的 API 怎么调、Issue 参数怎么转、GitHub 错误码怎么映射、写后怎么回读。

判断标准：公共机制里如果出现具体模块的业务词（github、issue、repo、token），说明抽错层了。

### 1.3 UI 分类不等于底层分类

UI 上有“软件开发页”“小说创作页”“对话页”，不代表底层要有“软件开发引擎”“小说引擎”“对话引擎”。

UI 页面是**交互集合**，它组合多个底层模块的能力；底层模块是**功能单元**，它被多个 UI 页面复用。两者是多对多，不要求同名、同层、同数量。

### 1.4 工作流模板是配置，不是运行时

软件开发、研究、小说创作都是可编辑的工作流模板。模板负责“选哪些 Agent、哪些工具、哪些连接器、哪些资源、什么工序、什么审查方式”，不复制底层实现。

模板不是第二套操作系统：它只组合已有能力，用固定的一小组步骤类型，不允许内嵌脚本，不允许自定义运行时。

修改一个使用实例，不应自动改变其他实例；修改模板，也不应静默改变已运行实例。模板与实例必须分离。

### 1.5 Context 是工作域，不是所有者

Context 可以组织或关联对话、Agent、任务、资源、连接、其他 Context、工作流配置和记录。但：

- Context 不是这些对象的强制所有者；
- 对象可以独立存在，并与多个 Context 关联；
- Context 关联某个对象，不产生对该对象的权限；
- 删除 Context 不应级联删除对象。

这些必须落到数据模型和代码边界里，不能只写在产品文档里。

### 1.6 工程要适合 AI 长期施工

每个完整模块应能让一个 AI 独立理解和维护。模块附近要有：职责与边界、公开接口、依赖、数据、测试、修改注意事项。

AI 修改某模块时，必须能明确知道：什么代码属于它、什么对外、什么内部不许依赖、哪些改动要跨模块协调、怎么验证。

## 2. 两条调整线

| 调整线 | 从 | 到 |
|---|---|---|
| 目录 | 按技术层（core / service / host / network / auth / storage） | 按维护单元（apps / modules / platform / tools） |
| 写法 | 中央注册、中央分发、到处加分支、UI 里写业务 | 能力声明驱动、模块内闭环、公共管线统一裁决、UI 只消费接口 |

两条线缺一不可：

- 只改目录：新目录很快会被旧写法重新填成“平台层里塞业务”。
- 只改写法：没有物理边界，import 图和依赖图无法自动约束，边界会在半年内被绕过。

## 3. 判断标准（可验证，不靠感觉）

架构改得对不对，不看图画得漂不漂亮，看四个结果：

### 3.1 局部性

给 GitHub 增加一个 Issue 能力，模块外改动不超过 2 个文件（模块清单/索引），公共调用管线、权限、账本、组合根零业务改动。

### 3.2 可删除性

删除某个模块（例如 AI API 能力），内核、其他模块、UI 壳仍然能编译、能测试；只有组合根允许失败，且失败信息明确。

### 3.3 并发行

两个 AI 同时改两个模块，代码目录零冲突；只有公共契约需要协调，且契约变更有固定流程。

### 3.4 可理解性

新来的 AI 只读该模块的 `MODULE.md`，就能在没有人类解释的情况下完成一次修改，并知道怎么验证。

四条有任何一条长期不成立，说明目录或写法需要修，而不是“这次特殊”。

## 4. 非目标

以下不是本架构的目标，不要用它们来评判本方案：

- 不是微服务化，不要求模块独立进程/独立部署。
- 不是动态插件系统，不要求第三方插件 ABI、插件市场、热更新。
- 不是通用工作流引擎，不要求模板能表达任意编程逻辑。
- 不是通用权限引擎，不要求现在实现完整 ACL/策略语言。
- 不是通用对象数据库，不要求 EAV 或图数据库。
- 不是记忆/知识引擎，不要求现在确定数据库或向量方案。
- 不是一次性重构，不要求现有代码全部重写。
- 不是目录美学，不要求所有模块目录长得一样。

## 5. 代价意识

这套架构不是免费的：

- 契约、模板、检查工具都要先投入；
- 每个能力模块比“写在一个文件里”多几个文件；
- crate/模块变多会增加编译与调试成本；
- 公共契约升级会牵动多个模块；
- 如果连接器长期少于 3 个、工作模式少于 2 个、维护者只有 1 人，这套结构的收益可能低于成本。

所以本方案同时给出“首版最小形态”和“何时不划算”的判断，避免为了架构而架构。

## 6. 一句话

**中央可以有机制，不能有业务；模块可以各自完整，不能各自重造安全语义。**
