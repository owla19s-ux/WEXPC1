## 2. 先分清“新增厂商”的两种情况

A. 厂商兼容现有协议，只改变地址、模型名和配置：应优先使用已有适配器与新增连接配置，不要求复制代码或安装新运行时。

B. 厂商具有新的请求、响应、鉴权或流式协议：需要新适配器；本次用 B 验证扩展边界，面板随包提供或复用通用配置面板。

维护单元是厂商／协议功能包；发布包可以包含声明、协议实现和专属面板。它不必对应一个进程，也不承诺所有复杂功能只能写一个文件。简单协议修改可以只动一个实现文件；测试和发布声明仍属于同一维护单元。

## 3. 三种责任分配方式

| 方式 | 好处 | 代价 |
|---|---|---|
| 插件自行管理调用、记录、取消和恢复 | 插件自由度高，宿主初始较薄 | 厂商重复实现公共机制，关闭或更新插件容易丢失权威记录 |
| 宿主只允许插件做纯协议转换 | 公共网络、记录和取消容易集中管理 | 特殊鉴权、多步骤协议可能迫使宿主不断增加厂商特例 |
| 插件负责协议会话，WEX 负责公共调用协调 | 保留协议差异的局部性，同时统一可观察状态 | 必须明确插件可使用的网络、凭证和生命周期边界 |

本轮推荐第三种作为试点假设，不作为用户已批准方案。若大多数协议可由纯转换表达，也可在第三种下优先使用受控网络服务与纯转换适配器；不强制每个适配器自建网络循环。

这里的“WEX”指公共服务责任，并非一个巨大的宿主文件，也未决定具体目录或进程。插件运行于宿主进程、独立进程还是其他环境仍未选择。

## 4. 从放入模块到完成调用

下表所有责任归属都是候选。名字表示逻辑职责，不要求立即新建同名模块。

| 用户动作／事件 | 候选责任分配 | 用户可观察结果／需要解决的问题 |
|---|---|---|
| 将完整包放入扩展目录 | 扩展管理读取声明，检查完整性、兼容和冲突 | 看见待加载、可加载或具体失败原因；复制一半不能执行 |
| 加载包 | 扩展管理协调后端准备与 UI 贡献发布 | 必需部分失败不能呈现“已就绪”；无专属 UI 可复用通用面板 |
| 填写地址、模型和凭证 | 模块面板解释厂商配置；连接管理保存连接身份及配置；凭证服务保存秘密 | UI 草稿与已保存配置分开；新建连接不等于获得调用授权 |
| 点击发送 | 会话／调用协调固定本次输入、连接配置修订和实现代次；授权边界检查调用资格 | 有一个可追踪的调用；不要求普通聊天先建立 Task |
| 请求厂商 | 适配器转换输入、进行协议交互并解释厂商事件 | 聊天页不导入具体厂商；协议是否直接联网仍待验证 |
| 输出流式内容 | 适配器报告事实；调用协调核验顺序与结束；会话保存消息；UI 展示 | 半截文本可显示，但不能因连接关闭就标记成功 |
| 模型提出工具调用 | 适配器报告完整工具意图；工作循环决定是否请求执行；执行边界另行授权 | 模型返回工具名不等于已获准或已执行 |
| 用户取消 | 调用协调记录取消请求，通知适配器停止；适配器报告实际观察到的结束 | 区分取消请求、停止本地接收、远端是否停止；不承诺退款或撤销已发生操作 |
| 完成或失败 | 调用协调收敛本次调用记录；会话记录部分或完整消息 | 保留部分内容和已知用量；未知用量不写成零 |
| 重载页面 | UI 重建订阅并读取权威状态 | 页面消失不能自动抹掉运行记录；断开页面是否继续生成仍需确定产品行为 |
| 更新／停用扩展 | 扩展管理关闭新准入；调用协调报告占用并排空或取消；再释放旧代次 | 新调用不误入旧实现；旧调用不被悄悄转交新版；历史连接与消息保留 |

“协议会话”仅指一次厂商交互内部的流、握手等状态，不拥有 WEX Conversation、Task、授权或正式操作账本。

## 5. 状态不能合成一个 running

| 事实 | 候选权威维护方 | 不应混同 |
|---|---|---|
| 包被发现、是否激活、当前代次 | 扩展管理 | 连接可用、调用成功 |
| 用户连接、配置修订、秘密引用 | 连接管理；秘密值由凭证服务管理 | 插件临时变量、UI 草稿 |
| 本次生成请求的准入、进度及结算 | 公共调用协调 | 插件加载状态、Task 状态 |
| 消息、部分输出和会话引用 | 会话领域 | 网络缓冲区 |
| 协议解析、网络句柄、厂商游标 | 适配器本次实例 | 可作为全局权威的调用账本 |
| 授权及撤销事实 | 权限服务 | 面板按钮是否可点 |
| 工具实际执行及证据 | 公共执行服务 | 模型提出工具意图 |
| 任务目标和完成验收 | 工作领域 | 一次生成结束 |

最大的未决点：公共调用协调放在 API、会话，还是复用 execution？

本轮建议先把责任写清，不新增一个万能执行平台。普通聊天与 Agent 都可能调用模型；若协调完全放在会话领域，需避免连接能力反向依赖会话。若复用 execution，需证明其能表达流式生成和未知结果，而不是套上不合适的工具操作状态。可在窄试点比较“API 内协调服务”与“复用现有 execution”的改动量，再确定位置。

## 6. 用故障反推边界

1. **复制中、声明冲突或依赖缺失**：不调用模块初始化；既有注册保持有效。
2. **后端可加载而必需面板失败**：撤回新代次的可见注册；失败清理若无法完成，应保留错误事实，不能伪称全部回滚。
3. **调用中修改地址、模型或密钥**：本次绑定不静默改变；凭证修订如何维持、撤权如何即时阻止后续动作需要实现验证，不能缓存旧授权永久使用。
4. **超时／插件崩溃**：保存已接收内容与结果未知事实；不自动重发可能已经计费的请求。协议明确支持幂等时才能讨论受控重试。
5. **取消与完成同时发生**：保留取消请求和实际完成证据，按一致规则只结算一次；取消按钮被点击不能覆盖已确认成功。
6. **更新时仍有在途调用**：推荐首个试点拒绝直接替换，显示占用，允许等待完成或请求取消。已进入停止接收后，新请求得到明确反馈，不悄悄排到新版。
7. **新版本准备失败**：尚未破坏旧版数据时保持旧版可用；数据迁移后不能仅换回旧文件就宣称回滚。
8. **插件要求新权限**：升级不能继承未授予的新权限；可被发现与可调用分开。
9. **停用后查看历史**：通用消息／结果仍可阅读，不以插件仍安装为前提。

这些是建议的行为验收条件，不是完整的状态机。尤其“本地取消”与“远端结果未知”可能同时成立，后续契约应分别记录，不能粗暴塞进一个 success/failed/cancelled 枚举后丢失信息。

## 7. 局部性检查

| 修改 | 预期修改范围 | 说明 |
|---|---|---|
| 兼容厂商新增连接 | 用户配置 | 不应新增厂商代码分支 |
| 新协议，已有能力范围内 | 新协议包内声明、实现、测试，必要时专属面板 | 不改总设置页、聊天页或 Agent 的厂商分支 |
| 改厂商参数布局 | 包内配置面板 | 不改公共执行规则 |
| 修正某协议流解析 | 包内适配器及测试 | 不改会话页解析逻辑 |
| 新增通用能力，如此前没有的媒体类型 | 适配器与公开能力契约及消费者 | 合理跨模块变更，不能承诺永远只加一文件 |
| 修改统一取消语义 | 公共协调与契约，相关适配器兼容验证 | 属于公共行为变化，不能伪装成单模块修改 |

如果每新增厂商都修改中央枚举、总面板 import 列表和聊天分支，局部性验收失败。如果所有模块代码都能随意读写公共数据库，同样失败。

## 8. 这次推演能与不能得出的结论

可以继续验证的候选：厂商差异聚合；公共调用协调独立于适配器寿命；连接身份独立于包版本；UI 不成为运行状态的唯一保存位置。

仍不能冻结：
- 调用协调与 execution／Agent Loop 的具体边界。
- 信任模型、网络／凭证访问方式与故障隔离。进程隔离不自动等于安全隔离。
- UI 动态挂载、关闭页面后的行为及未保存草稿处理。
- 语言、运行时、跨进程协议、签名和发布格式。
- 目录到 crate／前端包的映射，以及完整迁移方案。

本例不能替代 Space、权限、模板等领域的独立边界检查，也不能证明“所有底层都能热替换”。目前不扩充语言，不把 Node 实验当作已选技术路线。

## 9. 下一步验证的最小范围

固定一个真实 Rust/Tauri 宿主基线，用两个版本的模拟厂商协议和一个配置面板，验证：
- 构建宿主时未知的包可在不退出宿主时加入，后端与 UI 都实际使用；
- 页面重载、流式响应、取消竞争、适配器崩溃和在途更新有可观察结果；
- 相同调用只有一份权威记录，旧代次事件不能污染新调用；
- 新增协议所改文件集中在包内，没有新增中央厂商分支；
- 记录运行时分发体积、依赖数量和维护接线，不只统计源码语言。

这是后续试点建议，本次未启动实现。已有 Node 实验只验证其 README 记录的局部机制，不能计作真实桌面加载与隔离通过。真实厂商协议、Windows 打包、凭证隔离和数据迁移另列验证，不由模拟协议通过代替。
