# WEXPC1 当前研究共识与施工边界（2026-10-30）

> **性质：研究决策摘要，不是新架构、新版本计划或已实现功能声明。** 用这一页汇总最近讨论，减少反复追加同一内容。详细技术证据仍以 [工作流编辑器](../workflows/editor/README.md)、[DSH 双路线边界](WEXPC1-DUAL-PLUGIN-SYSTEM-BOUNDARIES-2026-10-30.md)、[DSH 运行报告](../dsh/README.md) 为准。与先前“首版 WEX 插件采用 Cordis”“编辑器数据可直接作为 WEX 业务数据”的暗示冲突时，以本页最新边界为准。

## 1. 定位与分工

- **WEX 主体**：Space / Group / Context 组织工作、角色、知识与资源；WEX 持有授权、任务/状态、操作回执、跨图关联等业务权威，不以 React Flow、Cordis 或外部 Agent 的内部状态为权威副本。
- **内部连接层 + 公共连接/适配层**：现有连接体系中的两类职责，不新造“插件墙”子系统。内部服务按需接入公共能力边界，外部工具和插件通过受控入口双向交换能力。对外暴露最小授权能力，不交出内部服务实现或完整 Context；真实安全边界另需进程/系统隔离，不能单凭接口限制。
- **内置连接器优先**：WEX 的基础能力通过可独立维护的连接器接入，连接器不承担 Space/Context 组织、调度状态权威或权限账本。现阶段应优先研究 **Agent 客户端连接器**，让外部 Agent 承担复杂执行；API、本地文件/Git、GitHub 等保留为 WEX 的基础操作、独立核验、恢复能力，不追求自建大量重复工具。
- **DSH 两条路线完全不同**：`dsh/` 是内置 Cordis Core+Loader 原生插件兼容实验宿主，目标先达 Windows 真机可加载、执行、卸载并检查真实插件；`connections/dsh/` 连接独立 DSH Agent，目标任务交接与真实回执闭环。两者互不依赖、不共用加载器。WEX 自有插件机制 `plugins/` 仍未定型，不要求首期采用 Cordis 或开发安装市场。

## 2. 工作流编辑器是视图研究，不是数据或执行引擎

- **React Flow = 目前使用的二维图形交互组件**：负责显示、拖拽、连线、选择、缩放和布局。当前 `workflows/editor/prototype/` 的 `model.mjs` 仅是临时草稿模型；不冻结 WEX 的数据结构/节点协议，不作为调度器。
- **WEX 视图引擎是重要的长期架构研究**：业务对象描述“是什么”，专业模板描述“如何理解”，视图表达“如何展示/编辑”；面向软件开发、科研、管理等不同专业场景。相同显示名称（例如“审查”）不保证相同业务语义和运行机制。当前每类一个节点视图文件仅是降低原型修改耦合，不是最终模板节点类型规范。
- **绝大多数架构树/进度节点图不执行**：需求、模块、任务进度、验证等图主要承担组织、理解和状态展示。执行工作流是单独类型；**数据关联 ≠ 执行依赖；映射存在 ≠ 状态必须完全同步**。一个任务阶段变化可让其他图投影不同的进度/待验证状态。
- **多架构树映射方向明确但暂缓实现**：共享稳定对象身份、独立关系映射和视图布局；树内显示编码可以变化，不应作为唯一绑定身份。编辑图时可暂停关联变更传播、隔离草稿，比较修订后发布；不能默认锁死所有其他图或中止运行任务。上述均是设计方向，非现有实现。
- **二维/多视图/三维是可替换呈现方式**：三维仅用于确实帮助理解复杂交叉关系的场景，不预设必须实现；不同图形技术不应决定 WEX 的业务数据。PC 到位后通过真实鼠标、窗口和交互使用研究，而不是现在冻结图层或协议。

## 3. 数据持续性与并发是更难的长期问题

- **难点不是简单节点连线，而是重启、断连、重试、跨 Context、多 Agent 并发后保持可验证的一致性**。WEX 需区分任务意图、调用尝试、外部执行事实、产物、验证和最终验收；结果未知不能冒充失败或成功，防止重复派发产生副作用。
- 编辑器不拥有任务执行，关闭图/切换 Context 不应自动取消既有任务；执行应使用明确版本的工作定义。并发配额、文件资源冲突、恢复策略和后台运行方式留待真实工程验证。
- 规模研究样本：5–15 项目，每项目约五张图，每图 5–20 节点（共 25–75 张图、125–1,500 节点）。这是**总体保存量，不是同时渲染量或并发任务数**。正式性能能力尚未测量；图实例/草稿须分开管理，不把所有项目塞进一个 React State。

## 4. 现阶段做什么 / 不做什么

| 方向 | 当前行动 | 延后到 PC 实测与后续设计 |
|---|---|---|
| React Flow | 保留独立编辑器原型，继续研究简单节点交互、不同展示方式；现有 DOM/模型/构建历史结果可参考 | 正式映射数据层、专业模板执行语义、多图联动、三维、75 图性能实测 |
| DSH 内置插件兼容 | 维护独立 Core+Loader 原型，准备真机对真实插件逐个做装载/依赖/错误验证 | 完整 DSH 服务生态、商店、任意插件兼容承诺 |
| 外部 Agent 连接器 | 优先确认 DSH 等客户端真实可用的交接入口与结果/产物回执；保持与内置插件宿主分离 | 预设不存在的 Agent 控制 API 或全量替代外部执行平台 |
| WEX 基础设施 | 连接器/授权/可持久化任务状态和结果追踪以稳定可检验为目标，复用外部执行能力 | 过早实现 WEX 动态插件平台、统一跨机制底层签名、全套通用图引擎 |

## 5. 验证与协作约束

- **研究样本不等于正式方案**，设计语义可以先确认，实现契约必须等 Windows/Electron 和外部实际连接验证；实验成果逐个纳入，不让单一库绑架主线。
- 工作流编辑器此前 5 项模型 + 5 项 DOM 集成、构建及 HTTP 预览有历史报告；后来按节点视图拆文件、新增测试，**重构后构建与测试仍待重跑**。真实浏览器鼠标交互因云端环境阻断，留给可用 Windows 真机测试，不声称通过。
- 仓库目前主要是设计和独立实验，不是已交付 WEX 应用。**不为研究结论批量创建空目录、接口、版本排期或更多重复文档**；尽量更新这份摘要及对应职责文档。
- 不主动触发 GitHub Actions；测试要注明实际执行的命令、环境及未覆盖项。
