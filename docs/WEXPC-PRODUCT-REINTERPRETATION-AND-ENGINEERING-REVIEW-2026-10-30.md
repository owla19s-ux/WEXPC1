# WEXPC 产品需求重新理解与工程偏差审查（2026-10-30）

> 状态：**讨论形成的产品认知与审查草案，供 WEXPC1 架构研究使用；非已冻结版本基线、ADR、接口协议或施工命令。**  
> 范围：WEXPC 0.1.1～0.1.5、WEXPC1 的目录和 AI 施工方法。  
> 来源：2026-10-30 用户与 AI 的连续讨论；对照 WEXPC main 的 `docs/PC-PRODUCT-AND-TECH-BASELINE.md`、`docs/WEXPC-0.1.1-IMPLEMENTATION-PLAN.md` 和 WEXPC1 当前目录草案。  
> 本次仅整理文档：不改 WEXPC 代码、不触发 Actions、不宣称工程验证通过。

## 1. 最重要的纠偏：需求被技术解释过度复杂化

用户描述的主要是**使用行为与组合方式**；此前 AI 经常立即把需求推导为多套独立实体、技术子系统、实现契约与测试工程，导致原本约“1”的使用需求被扩张成约“2.5”的架构与施工范围。并非已有技术研究都无用：授权、可靠回执、并发冲突与恢复确实必要；错误在于将**内部保障手段误提升为新增产品功能与用户强制流程**。

今后严格区分：
1. **用户功能**：用户或 AI 在界面/对话中能做什么；
2. **公共基础能力**：API、工具、连接、权限、调度、真实执行、数据和证据；
3. **使用组合**：Context、工作流、模板与视图如何按需使用这些能力；
4. **技术实现/验证**：接口、协议、进程、数据结构、故障测试等，必须为上述目标服务。

不得为了“架构完整”凭空增加管理平台或固定层级；也不得为了简化而删除必要的权限、安全、执行事实。

## 2. 目前重新明确的产品模型

### 2.1 Context：可自由组合的工作环境
- Space → 可选 Group → Context 是组织与呈现结构，不是工具执行层级；Context 不等于软件 Project。
- 在一个 Context 中按需关联 **0..N 个 AI、资源地址（可有名称/备注）、公共连接、工具、工作流以及相关工作对象**；可以只选其中少量，不强制创建项目、任务、Agent 队伍或工作流。
- 同一能力/对象可被多个 Context 引用，解除关联不删除对象；组织归属不自动授权。
- 普通对话应能不依赖 Context/工作流/项目而独立使用。

### 2.2 连接系统：公共能力池
- API、GitHub、本地文件/终端/Git、后续外部 Agent 客户端等是可接入、管理、按需选用的**公共设施**。
- 配置一次的可复用连接，可供不同 Context/普通对话引用；不同场景分别检查实际使用范围与授权。
- **已安装/发现、Context 已关联、当前获授权、实际执行成功**是不同事实。
- Connector、Adapter、协议、凭证、运行时插件的设计是支撑机制，不代表要给用户开发一套额外的“连接管理平台”。运行时加入模块且不重建/重启主程序是 WEXPC1 已记录的设计目标，但所需技术和产品版本尚待验证/安排。

### 2.3 AI：选择、配置、使用、分工，而非强制组织架构
- 用户可直接选择 API/模型聊天，也可为其配置名称、角色表现、工作职责或作用范围；同一模型可多处使用、承担不同工作。
- 可把不同 AI 指派到工作流的施工、审查、研究等节点；工作职责不等于资源授权。
- Persona/Duty/Agent/Session/Executor 等底层身份或状态区分如确有必要可保留，但**不得成为普通用户开始聊天、创建 Context 或使用一个 AI 的必经多层配置**。
- 首版不建设完整长期记忆系统；普通配置、任务、历史与结果的持久化不等于长期认知记忆。

### 2.4 软件开发模式：工作流组合 + 共用数据 + 面向人的视图
- 软件开发**不是独立项目管理平台**，而是 Context 中一种可选的工作模式/预设组合：开发相关资源与工具、AI 分工、工作流、工作数据及 UI 视图。
- 用户或授权 AI 能创建/修改工作流，安排节点与先后/条件/退回关系，把 AI 分配至节点；用户、主 AI 或其他获授权主体可创建任务卡并交给工作流。
- Dispatcher 按程序化规则接收任务、派发到节点执行者、收取结果，依成功/退回/阻塞等事实推进；AI 进行具体认知与工作，Dispatcher **不替 AI 作技术判断**。
- 任务板/项目进度板是**人和 AI 共用同一批工作数据的操作和展示入口**，不是另一份独立状态。需求树、功能树、架构树、模块到代码文件的映射、谁在施工、测试/审查结果等，属于对象及其关系、任务状态/证据在 UI 的不同投影。**保留这些功能，但不能由此推导出独立的需求管理/架构管理/项目管理系统。**
- 不同工作模式可复用工作流、调度、连接、授权、证据机制；小说、研究可有不同预设和专属视图。工作流可以不用多 AI，普通聊天也可以不用工作流。
- 对在途工作流的编辑需要明确新版本生效边界；模型口头报告与真实工具结果/独立核验不得混同。

### 2.5 典型验收操作（用于指导设计，不是实际测试通过）
Windows 启动 WEX → 配置公共 API/本地工具/GitHub → 创建开发 Context → 关联代码/资料地址、选若干 AI 和适用工具 → 从预设或空白创建可编辑工作流 → 将 AI 指派到施工/审查节点 → 人或 AI 建任务卡并放入工作流 → Dispatcher 真实派发、回收工具结果、交接审查 → 审查通过继续/退回修复/异常阻塞 → 人与 AI 在同一数据板看进度、关联需求/架构/文件/证据，并可调整未来工作。独立普通对话和无模板 Context 同时保持可用。

## 3. 现行 0.1.1 的具体偏差与保留要求

对照产品基线 §0.3.1、§5.1.1～§5.3 与施工计划前/中/后、P1～P6：

| 现有表述/实践 | 风险或偏差 | 候选纠偏 |
|---|---|---|
| Persona、Duty、Agent 实例、Model、Session 等作为最低配置流程 | 用户使用 AI 前被迫理解复杂实体 | 简化对外配置；必要执行身份/权限区分藏于基础机制 |
| “轻项目管理 × Dispatcher × 多 Agent 施工”三系统贯通 | 将一套工作流的不同职责设计为三套独立产品 | 以共享任务数据 + 工作流 + 程序化调度 + 多执行者的**一条用户闭环**审查 |
| 软件开发模板必须先做需求/功能树、页面/架构关系投影，再后期执行 | 数据视图被误设为工作流可执行的前置 | 保留结构树和文件映射，但检查前后依赖；优先实现能编辑/运行的基础工作流 |
| AI 可从对话提出项目结构草案 | 没完整覆盖经授权 AI 创建/修改 Context、工作流、AI 关联、任务的使用行为 | 审查自然语言与手动操作共用业务入口；明确首版可操作范围 |
| 0.1.1 多 Agent 与 Dispatcher 强要求、0.1.2 才有完整画布 | 基础工作流编辑可能缺位 | 区分**基础节点/流转编辑（建议考虑 0.1.1）**与**自由画布/丰富拖拽（可后续）**；新增范围待确认 |
| 各模块大量契约/模拟测试 | 职责尚不稳，验证了可能被废弃的模块边界 | 先收敛用户行为、职责、候选目录；仅针对阻碍边界决策的风险试验 |

**明确保留**：Context 非 Project 且自由组合；公共连接能力；权限与关联分开；任务/工具真实回执；已授权范围连续执行；两个 AI 互不覆盖的实际并发；可核验测试和审查；结果未知不盲重试；Windows 能开发 WEXPC/Android 的真实闭环。以上不因去复杂化自动取消。

**不在首版新增**：完整长期记忆/公共策略库、完整插件市场、多租户/云服务、复杂多项目自治等。动态扩展作为设计目标而非已实现承诺。

## 4. 后续版本的审查意见（不等于批准改期）

| 版本 | 现有主要方向 | 重新解释及待确认点 |
|---|---|---|
| **0.1.1** | 通用基础 → 开发模板 → 真实施工 | 以自由组合、基础可配置工作流、共享数据板、真实调度/施工为核心；基础工作流编辑是建议补齐的功能空白，**尚未正式变更版本要求** |
| **0.1.2** | 高级关系、画布、多视图、语音候选 | 着重改善已有数据/工作流的人机交互：自由画布、拖放、视图联动，不应新建第二套业务状态；语音归属待确认 |
| **0.1.3** | 多 AI 协作深化 | 扩展跨项目/多工作流并发及高级协作，而非首版才出现基础 AI 分工 |
| **0.1.4** | 跨环境/设备/连接 | 增加远程、移动端、外部客户端及工具来源，复用公共连接与调度，不另建独立宿主；外部 Agent 兼容细节仍需研究 |
| **0.1.5** | 其他模式、知识、角色/账号/云 | 聚合了不同成熟度的长期方向，**不应作为已冻结的整体版本承诺**；小说/研究预设可复用既有机制，记忆/云/发行另行研究 |

现行文档的版本及验收条款**没有因本审查自动失效**。所有范围新增、删除、前移、后移均需后续单独确认并同步权威基线；严禁偷偷改产品范围。

## 5. WEXPC1 代码目录设计与原工程施工问题

### 5.1 根本问题
此前 WEXPC 虽有模块化意图，实际代码按技术层、主入口及跨域调用累积，局部 UI/业务修改可能涉及多个中央文件；功能职责未先稳定，随后新增 Agent/Task/权限/执行契约，造成修改局部性不足和长期维护风险。不能把“已有某些测试通过”误判为用户所需组合功能已闭环；也不能未经实机运行断言所有实现不可用。

### 5.2 目录应从职责推导，而非反过来决定需求
1. 从实际用户流程和版本功能清单归并**独立能力与组合/视图**。
2. 明确各功能拥有的正式数据、允许操作、不拥有的职责、与相邻功能协作关系；一个逻辑职责不必对应一个顶层目录或进程。
3. 再形成候选物理目录及代码迁移映射，以**修改局部性**验收：改某个连接器通常主要改其目录；改开发模式展示不应改公共调度；改工作流规则不应改厂商协议。
4. 每个实际维护单元就近放 `MODULE.md`（或明确一致的说明文件），说明职责/非职责、公开能力、依赖、权限边界、修改位置、测试范围、常见陷阱；机器清单负责可检查的注册元数据，避免多份手写真相。
5. UI 和相关的模块配置/视图尽量就近维护；不要求“所有目录都是运行时插件”，也不先生成几十个空壳。
6. 普通业务改动优先局部完成；必要公共接口变动可跨模块，但要说明原因、影响和验证。**目录结构不是架构本身**，仍须行为验收和可维护性证据。

### 5.3 AI 施工方法纠偏
- **旧倾向**：从技术抽象出发 → 扩展实体/职责 → 生成大量契约和独立测试链 → 再试图找 UI/目录落点；多批次补局部原语，端到端用户功能迟迟不闭环。
- **建议顺序**：真实操作场景 → 产品功能与职责 → 可复用公共能力 → 候选模块目录/就近说明 → 针对关键阻塞验证语义及实现技术 → 一条实际用户纵向链路 → 逐步扩展。
- 一项技术试验必须明确：**验证哪个用户行为、哪个职责分界、影响哪个目录或施工选择、失败会改变什么决策**。只验证模拟行为不等于 Windows/Tauri/实际加载已通过。
- AI 应主动核对仓库、实施、执行本地可用测试、修复并报告真实 SHA/证据，不让用户反复转交碎片任务；遵循主仓工程授权与 Actions 成本规则。
- 新增独立子系统/公共契约须论证“现有能力组合为何不足”；允许严谨的内部安全机制，禁止把技术复杂度转嫁成不必要的产品交互。
- 先做可工作样本，再用跨模块改动范围、状态一致性、异常行为复核目录；不以仅文件重排冒充架构完成。

## 6. 建议下一步研究顺序与明确未决项

**建议顺序（非施工授权）**：
1. 建立 0.1.1 全量用户行为清单及后续版本对照，将“功能/组合/视图/底层保障/工程验证”标注清楚；
2. 以软件开发 Context 的单条完整工作流贯通场景，确定功能责任与共享数据的业务语义；
3. 对照旧代码与 WEXPC1 候选目录形成**代码归位/保留/拆分/废弃建议表**，并示范若干真实模块的就近说明；
4. 只针对会改变模块边界的风险开展受限验证，包括基本调度循环、权限和可靠回执、真实运行时加载；
5. 复核 0.1.1 与 0.1.2 的基础编辑/高级画布边界后，**由用户确认**是否修订正式产品基线和施工阶段顺序。

**仍需讨论**：基本工作流最小编辑粒度；人和 AI 修改运行中流程的生效规则；共享数据中需求/架构/代码引用的可编辑与证据边界；插件运行时实现机制与具体版本；当前 Rust/Tauri/React 的维护目录到编译/打包结构映射。**这些尚不能冻结函数签名、文件布局、持久化表和协议。**
