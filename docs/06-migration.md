# 06 — 迁移方案：从现有仓库到目标结构

> 原则：**不搞大爆炸，不重写已验证的安全实现，不保留两套并行真相。** 迁移是一系列可验证的小步，每步都有退出条件。

## 1. 迁移原则

1. **先定规则，再动代码。** 没有 MODULE.md 模板、依赖矩阵、契约草案，不要开始搬目录。
2. **先试点，再推广。** 用一个模块验证规则，规则被证伪就改规则，不要一次铺开。
3. **先适配，再重写。** 已验证的安全/持久化实现优先包一层适配，不轻易重写。
4. **一次只保留一个真相。** 迁移过程中不允许 Rust 和 UI 同时维护同一业务状态。
5. **可回滚。** 每步都能回到上一步；不删旧代码直到新路径验证通过。
6. **验收不是“能编译”。** 是“新增功能局部完成 + 删除模块可编译 + 并行施工不冲突”。

## 2. 迁移步骤

### 步骤 0：定规则（1-2 周）

产出：

- `docs/00-intent.md`、`01-repository-structure.md`、`02-coding-rules.md`、`03-module-contract.md`、`04-dependency-rules.md`（本仓已有）
- `templates/MODULE.template.md`、`module.template.toml`、`NEW-MODULE-CHECKLIST.md`
- 一份 ADR：模块边界与依赖方向

退出条件：

- 团队（或 AI）能用模板回答“新功能放哪、怎么暴露、怎么测”；
- 对“什么进 platform、什么留 module”有一致判断。

风险：规则写得太抽象，无法执行。对策：每条规则必须带检查方式。

### 步骤 1：搭骨架（1 周）

产出：

- `apps/desktop`、`apps/ui` 最小可运行壳；
- `platform/contract` 最小版（ID、能力描述、调用、回执、错误）；
- `platform/{store, secrets, host}` 最小实现；
- `modules/` 空目录不建，只建第一个试点模块；
- `tools/arch-check`、`tools/testkit` 雏形。

退出条件：

- 空壳能启动、能跑一个 demo 能力；
- `arch-check` 能对当前依赖图报错/通过。

风险：过早建全部 platform 机制。对策：只建试点需要的，其余按触发条件后补。

### 步骤 2：试点一个模块（2-3 周）

选 GitHub（或本地文件）作为试点，因为它同时有认证、网络、读写、错误、证据。

产出：

- `modules/github` 完整实现 + 能力声明 + 契约测试 + 回放；
- UI 一个最小入口能调用；
- 验证“新增 Issue”改动面。

退出条件：

- 新增一个能力，模块外改动 ≤2 个文件；
- 公共机制零业务改动；
- 权限/记账/回执路径跑通。

风险：试点时为了方便临时改公共机制。对策：临时改动必须标记并进 ADR，试点结束前清理。

### 步骤 3：第二个模块验证契约（2 周）

选 AI API 或本地文件（与 GitHub 差异大）。

目的：验证契约不是为 GitHub 特制。

退出条件：

- 同一套 descriptor/invocation/receipt 不需要特例字段；
- 两个模块共享同一 testkit；
- 发现契约问题 → 改契约（走 ADR），而不是加特例。

风险：为第二个模块加大量特例。对策：特例超过 1 个就停下来改契约。

### 步骤 4：收公共机制（1-2 周）

从试点中抽取：

- 凭证存储（如果之前是模块自管）；
- 操作账本（如果之前是模块自记）；
- 权限判定组合（如果之前是 UI/模块各判）；
- 持久化/迁移框架；
- 事件/通知。

原则：**先有重复，再抽公共**。不要先造公共再找用途。

退出条件：

- 两个模块使用同一套机制，且机制里无业务词；
- 删除任一模块，机制仍能独立测试。

### 步骤 5：迁移第二个业务域（3-4 周）

例如 workspace/Context 领域：

- 先定义对象/关系模型（引用边，不是所有权）；
- 再定义持久化与查询投影；
- 最后接 UI。

退出条件：

- 同一对象可被多个 Context 引用，且不产生授权；
- 删除 Context 不级联删除对象；
- UI 只读投影，不维护第二份业务真相。

### 步骤 6：UI 改为声明驱动（2-3 周）

把工具列表、能力可用性、配置表单从手写改为从 descriptor/registry 生成。

退出条件：

- 新增后端能力，UI 无需手改（或只改展示文案）；
- 配置表单由 schema 生成，模块不写 UI 代码。

### 步骤 7：上护栏（持续）

- CI 接入 arch-check、contract tests、依赖图快照；
- PR 模板加“四问”；
- 每月统计：模块外改动数、契约变更数、跨模块 import 数、循环依赖数。

退出条件：

- 违规能在 CI 拦截，而不是靠评审记忆。

### 步骤 8：删旧路径

- 旧目录归档/删除；
- 旧协议/旧接口标记退役；
- 数据迁移完成并验证；
- 文档权威更新（superseded 索引）。

退出条件：

- 仓库里没有两套实现；
- 新 AI 不会误读旧路径。

## 3. 旧代码处置策略

对每个旧 crate/目录，选一种处置：

| 处置 | 适用 | 做法 |
|---|---|---|
| 复用 | 纯领域规则、安全实现 | 直接迁入对应模块，保留测试 |
| 适配 | 接口/存储/平台差异 | 包一层适配到新契约，不重写 |
| 替换 | demo/过期协议/临时实现 | 标记退役，新实现上线后删除 |
| 仅参考 | 历史 UI/实验代码 | 移到 `reference/`，不进入构建 |

**不要**因为“代码相似”就假定可复用；每个都要有测试证据。

## 4. 双真相风险与处理

迁移期最容易出现：

- Rust 和新模块都维护连接配置；
- UI 和新服务都维护组织状态；
- 旧协议和新契约都对外暴露。

处理：

1. 指定唯一权威（写入口）；
2. 旧路径只读或只转发；
3. 用开关切换，切换后旧路径失效；
4. 数据迁移脚本必须可重跑/可回滚；
5. 加“双写检测”测试：同时改两边，断言不一致会报错。

## 5. 回滚策略

- 每步迁移在独立分支/开关后；
- 数据迁移前备份；
- 新路径验证通过前，旧路径保留；
- 出问题时回退开关，不靠回滚代码；
- 归档旧代码而不是立即删除，直到确认无引用。

## 6. 迁移完成的判断

不是“目录建好了”，而是：

- 新功能只在模块内完成；
- 删除模块后系统仍可构建（除组合根）；
- 两个 AI 并行改不同模块无冲突；
- 依赖图无违规边、无环；
- 契约有版本、有契约测试；
- 旧路径已删除/退役，文档权威已更新。

## 7. 迁移中的常见错误

1. **先搬目录后定规则**：目录搬完，写法没变，很快长回原样。
2. **一次性重写**：风险高、无法验证、容易丢已验证行为。
3. **保留双实现“以防万一”**：永久双真相。
4. **为迁移方便在公共机制加业务**：污染机制。
5. **跳过试点直接铺开**：规则未验证，返工大。
6. **只迁移代码不迁移测试**：失去安全网。
7. **不设退出条件**：迁移变成长期状态。
