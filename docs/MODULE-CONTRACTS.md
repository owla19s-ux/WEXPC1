## 3. 提供/消费关系与依赖方向

以下是能力依赖，不是完整源码import许可表。提供方维护语义，消费者依窄端口；app注入实现。源码边、运行能力边、装配边分别检查，双向观察不强迫双向import。

| 提供方→消费者 | 必需能力/证据 | 方向与禁止绕行 |
|---|---|---|
| shared→各域/app | 提交成功/未提交/未知、权威修订回读、限定路径/秘密可用性 | shared不import领域实现，不自行解释Task/授权 |
| permissions→各正式入口与connections | 当前主体/入口/动作/资源决定和依据，非允许不得动作 | 事实宿主核验注入，permissions不反查所有领域私有库 |
| space→UI/views/对话/工作域 | 获准Context/组合引用、本体/关系修订和定位 | 外部文件版本另由实际资源owner提供，不把关联变授权 |
| AI→对话/工作域/选择投影 | 配置职责及本次不可变依据，当前获权历史解释 | 新工作准入与历史解释分开，不读“最新”覆写旧轮次 |
| connections→AI/对话/工作域/诊断 | 能力元数据、受控Operation、尝试观察/控制差异 | 消费者不解析厂商协议，connections不写Task或消息权威 |
| workflows→对话/UI/views/modes | 显式任务创建、定义/Task/核验投影和受控编辑 | 一般对话不必创建Task，视图不倒写任务 |
| workflows/runtime→connections（宿主注入） | 无Task也可用的资源协调依据/修订、未决占用和释放证据 | connections不能私有import runtime；预检与派发复核复用同一意图/协调引用 |
| 对应领域→connections回调（宿主注入） | 本次目标最小查询/写操作及领域修订规则 | 外部身份/范围每次核验，不给全Context/数据库 |
| 通用域→modes | 专业组合需要的通用创建/查询/编辑 | 源码依赖是modes消费通用出口；通用域不反依赖具体模式 |
| modes/领域→views | 专业规则身份/获准对象关系和来源版本 | views经注入消费；modes不导入views实现决定业务 |
| 领域窄桥→UI | 获准查询、意图提交、原关联恢复与状态证据 | renderer不导入Node/凭证实现；面板位置不改变业务owner |

装配根可以引用公开业务面和宿主专用装配面，不能以装配名义任意深导入private。运行回调端口可由消费者声明所需形状，但不能削弱提供方授权/版本前提。完整自动检查规则及例外管理见[tools施工规格](../tools/README.md)。

## 4. 四组优先边界审查结论

| 边界 | 责任收敛及重要失败例 | 相关契约 |
|---|---|---|
| Space↔Permissions↔AI | Space写选择、AI写职责、permissions写许可；解除关联/撤任不隐式删目标或撤权，后续资格仍按当前事实重判。入口B不能用入口A对同Context的许可；重装旧许可不复活 | SPC/AIC/PER行为样例；非对话入口映射D |
| Conversations↔Connections | 消息/逻辑生成与Operation/Provider分开；已落盘输入、外部接受、流式暂态、定稿保存分开观察。G1迟到不覆盖G2；重发是新生成，不重放未知工具 | 对话公开表+C01–C05；提交ACK丢失只读回、不再调模型 |
| Workflows↔Connections↔Permissions | 分配/准备不执行，连接宿主准入/保存attempt/适配；工作域按证据核验验收。runtime预检与最终准入绑定同一协调引用；Task与无Task同资源均受阻。所有非明确允许均零动作 | W01–W07+C02–C05+PER；unknown不释放占用、不盲重试 |
| Workflows/modes↔Views | 执行定义/依赖属工作域，专业对象关系属模式/原域，出现映射/布局属views；图上同名不等同机制。草稿不覆写运行结果，不直接采用ReactFlow Draft | W01/W07、modes与views；模式单向消费通用域 |

以上收敛没有新增全局状态管理器/协议总线/插件框架。四组的样例为设计验收要求，不是本轮已运行结果。原型证据只限定历史已测范围，未把参考函数提升为正式接口。

## 8. 后续专项：复杂交错操作链路压力测试（2026-10-31 需求记录；尚未执行）

**缘由**：L01–L12 是常规用户行为与基础异常覆盖，不能证明多个 Context、模块、执行者、窗口、安装代次、外部服务及数据盘在并发/断联/恢复条件下仍维持正确契约。第四批交叉审查还发现：普通领域提交与外部副作用不应机械共用同一去重机制；非对话入口第三层授权待确定；workflows↔connections 在持久派发/关联之间存在崩溃窗口；app/shared/permissions 的重装信任事实需明确唯一来源；模块能力应按成熟度分级。

**测试方法与边界**：以下 H01–H13 为**复杂业务场景/契约压力测试输入**，不是十个工程施工包，更不是对已有 L01–L12 的代码实现要求。先以桌面用户的完整操作、角色和真实资源为起点，交叉注入并发、故障、时序和恶意输入；逐步记录模块权威事实、权限判断、数据/回执流向及失败恢复预期。沿场景发现缺口后**按模块归并修改相应业务契约**，禁止在测试场景内新造并行的权限、任务、操作或视图状态机。静态场景审查≠运行通过；未来有真正模块实现后，才用替身故障注入、持久恢复及 Windows/外部 Agent 实测分级验收。

| 场景 | 交错操作与故障注入 | 优先核查的模块契约与不可越过的保证 |
|---|---|---|
| H01 跨 Space/Context 多 Agent 共享工作区 | Space A/B 引用相同独立 Context；两个 Agent 通过不同连接器修改同一 Git 工作树，第三个不经 Task 的工具也写相同目录；一路断连且结果未知 | space 引用不复制/合权；workflows/runtime 按实际资源/别名协调；connections 的无 Task 副作用同样受约束；未知占用不因退出释放；独立核对 Git/文件版本 |
| H02 权限撤销与在途执行赛跑 | 用户授权工具在排队；另一个窗口调整 Context/职责、撤销具体权限；已派发外部 Agent 继续写文件，旧窗口收到迟到“允许”/完成通知 | permissions 判权代次与派发前复核；AI 角色不代替授权；app/UI 撤权缓存；connections 与 workflows 分别保留已发生事实；撤权不谎称停止/回滚 |
| H03 多层提交 ACK 丢失与重启 | 创建消息/Task 后数据库提交成功但回复丢失；Operation 意图记录成功而调用外部时进程崩溃；外部执行成功但回执保存失败；用户重启后反复点击重试 | 分清领域写提交与外部副作用；原业务关联回读/attempt 取证；不同去重保留范围；不能凭 timeout、not found 或用户重复点击启动第二次写入 |
| H04 备份恢复与外部世界时间错位 | 用户备份后外部 Agent 修改仓库并产生提交；WEX 回滚本地旧备份，恢复时旧账本缺少新提交，仍有未决任务；另有丢失的 Context 数据盘 | shared 备份不承诺回滚外部事实；connections 重新观察，workflows 重新核验；缺盘不生成空本体；历史授权/证据不自动成为当下许可 |
| H05 安装代次、双 Windows 用户与残留进程 | 用户在 D 盘保留数据，卸载重装/系统重装后旧凭证仍可解密；第二 Windows 用户尝试接入同一根；旧 Agent 进程与旧 IPC 回调未结束 | app 提供可信生命周期事实，shared 做技术隔离，permissions 独占许可有效性；重装需重配凭证与授权；旧实例不能向新实例授权或写回；实际 Windows ACL/进程树待实机 |
| H06 DSH/Hermes/Codex 能力不对称 | 一个外部 Agent 能 query/resume 但不能 interrupt；另一个退出 CLI 只 detach 不停止执行；用户在连接器切换期间下达取消、继续和验收 | connections 按固定版本能力协商并保留 session/turn/backend/cwd；“停止请求”“已停止”“已退出”“已回滚”绝不混同；workflows 基于真实证据推进，不把各 Agent 拼成虚假的全能协议 |
| H07 多窗口 UI、视图投影与业务修改冲突 | 一窗口拖动多图布局并暂停传播，另一窗口修改真实 Task、第三个 Agent 更新专业关系；旧自动布局晚到、验收版本已变化 | views 布局/投影不拥有 Task 真相；modes 专业关系与 workflows 执行依赖分开；跨窗口 CAS/来源修订；旧布局不能覆盖手动修订，旧验收不能覆盖新产物 |
| H08 插件/模型输出跨信任边界攻击 | 第三方插件回调伪造角色/Context/授权；模型生成文本夹带“立即执行”的工具指令；过期插件实例重放请求或借宿主凭证跨目录读取 | app 可信身份绑定；permissions 逐入口/动作判权；connections 受控出口与最小能力注入；shared 凭证不得泄露；OS 级隔离与协议身份需单独验证，不把进程隔离当沙箱 |
| H09 跨模块部分完成与撤销误判 | 用户采纳专业模板创建 Context/角色/Task/视图；部分提交已成功、部分写失败，取消时另一窗口修改同一关系；用户选择重试或撤销 | 各 owner 保留局部提交真相和来源修订；明确可补偿/不可逆/未知；不得假设跨模块全局事务；不能因取消删掉已有共享 Context 或外部副作用 |
| H10 资源身份变动与安全并发 | 不同盘符/符号链接/大小写路径指向同一目录，Git worktree 共用元数据；运行中用户重定位数据根、替换工作区或安装更新；一个执行者继续使用旧身份 | shared/app 定位与重解析点检查；runtime 资源规范身份/失效；connections 派发前复核、旧窗口/旧实例结果隔离；身份无法确定时阻塞而非默认不冲突 |
| H11 Space→Git→工作流编辑器→AI节点→DSH→目录验收（完整操作） | 用户从创建 Space/独立 Context 开始，关联用户选定工作目录、Git 仓库及可选 GitHub 连接；在编辑器绘制节点、依赖关系，为任务节点配置 AI/职责与 DSH 执行能力；保存工作流版本，启动任务，经当次授权、资源协调、连接派发，在明确的 backend/cwd 下由 DSH 修改文件；WEX 关联 Operation 与 Task/节点轮次，核对目录身份、实际文件/git diff/commit、运行验证后由有权主体验收。注入：编辑时换 AI 或重连资源、保存失败/节点旧版本、同仓另一 Agent 修改、DSH 断连但已写文件、回执迟到、测试失败需新轮次、验收前文件再次变化、重启恢复 | space 只拥有组织/引用不复制仓库；workflow 编辑定义及节点执行关联由 workflows 维护，views/React Flow 只呈现与布局；AI 配置/职责不授予运行权；connections/local/Git/DSH 分别描述真实资源与操作，不拥有 Task 真相；permissions 按入口/实际资源判权；shared 保存而不裁决业务；workflows 以独立目录/Git版本/验证证据判断完成且拒绝将 DSH completed 当作验收。检查节点修订/派发版本绑定、工作目录不可由未授权文本替换、未知不重派、验收失败可追溯重做，最终用户见到清晰的产物与验收状态 |

| H12 DSH原生插件目录→真实宿主→能力使用→卸载恢复 | 用户指定WEX数据根的 `plugins/dsh/`，安装经版本/来源/依赖检查的真实DSH原生Bundle；DSH专属Core+Loader宿主加载并等待Service依赖，WEX界面观察就绪/缺依赖/错误；插件公开可用能力时由受控连接入口描述并提供给获准消费者，调用后接收实际结果；更新配置、热/重加载、停用、卸载、重启后复查插件和Service释放。注入缺Service、版本冲突、插件启动抛错、安装中断、旧实例迟到回调、插件无限挂起、撤权与卸载并发、残留进程、Windows中文路径/权限异常 | `dsh/` 独占DSH原生包解析、Cordis生命周期、Service就绪及原生兼容性；`app` 负责宿主进程装配/隔离及数据根接入；`shared` 负责技术目录/配置保存；`connections` 仅在插件能力进入WEX受控边界时负责发现/准入/Operation回执；`permissions` 唯一授权；`workflows` 按需要消费能力但不管理插件生命周期。`connections/dsh/` 是**外部DSH Agent连接器**，不是此插件加载器；`plugins/` 是WEX自有插件体系，不承担DSH原生兼容。必须分开报告：Linux已测Core+Loader/hello样本 ≠ Windows真实插件/真实依赖/宿主隔离/生产安装已通过。插件内部Cordis Service调用不自动具有WEX权限保护；独立进程本身不等于沙箱 |
| H13 内外连接墙双向组合与职责压力测试 | 用户在WEX的Space/Context中选择内置文件/Git/API或DSH插件提供的能力，经连接墙能力发现和受控装配后授权执行，保存真实Operation及观察；外部DSH插件或Agent经可信入口**反向请求**WEX某个领域的最小可读信息/允许的写操作，范围仅限当次目标；在任务编辑器/独立会话/无Task操作三种入口分别验证。注入能力列表变化、同名能力不同提供者、provider失联、只读与副作用误分类、来源身份伪造、跨Context扩大访问、旧授权复用、回调重放、回执落盘失败、双向调用形成递归/死锁 | `connections` 内部能力适配面只负责把**领域公开能力**封装为受控出口；公共调用边界负责能力发现、提供者/实例身份、准入接点、单次操作/回调观察与回执；具体连接器只管理厂商/设备协议和资源转换；`permissions` 独占授权决定，真实领域独占数据/修订与最终业务准入，`app` 装配可信入口，`shared` 保存技术记录，`workflows` 独占Task/资源占用/验收。内部正常模块调用不必都绕连接墙；外部回调不允许拿全局可变宿主或数据库句柄。能力注册不等于可调用、调用接收不等于成功、外部completed不等于验收。特别检查连接墙内部接口/公共出口/具体适配器/DSH原生宿主之间是否存在重复能力注册、双重账本、双向源码依赖或缺失的生命周期owner；根据链路按模块归并职责，**不另造一套连接墙平台** |

**每个场景的审查记录必填**：初始环境/用户身份与入口、逐时序操作及并发交错、涉及的模块公开能力、谁拥有哪条权威数据、授权和操作准入位置、外部副作用边界、崩溃/恢复分支、预期可观察证据、对照契约的漏洞与建议修改归属、验证方法与证据等级（静态推演/替身测试/真实服务/Linux/Windows）。包含“用户正常操作→多个模块交错→失败→重启/恢复→独立核验→最终用户结果”，不能只列技术异常名词。

**执行前的阶段门槛**：先完成第四批 P0 契约交叉收敛，再使用 H01–H13 评估是否仍存在业务语义缺口；必要时新增场景须说明未覆盖的独特冲突机制，不为数量扩写。可以先静态逐场景对冲，再按模块制定最小可运行故障夹具和独立验收；尚无正式模块实现，不得宣称复杂链路已经通过运行测试。不得触发 GitHub Actions 或无授权的付费外部 Agent 调用。**后续施工单位依然是模块，复杂链路只用于设计压力测试与系统组合验收。**
