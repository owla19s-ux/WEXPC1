# WEXPC 源码目录与 Windows 安装、数据存放要求

- 日期：2026-10-30
- 状态：用户确认的组织与数据要求；2026-10-30 已确认 WEXPC1 新实现优先采用 TypeScript + Electron + React，具体文件、IPC 接口、安装器及行为仍需实现与验证。
- 范围：源码目录、UI 组织、安装后文件存放和重装系统后的恢复要求。
- 本次只记录设计，不修改产品代码，不执行旧代码迁移，不调整正式版本排期；以下均不是已实现或已验证声明。

## 1. 设计依据

用户描述的是使用行为、组合方式和可见界面。代码目录应从实际需要的能力归并得出，不按每个产品名词建立独立系统。

Space／Context 负责组织、关联与呈现；软件开发模板是一种工作流模式。任务输入、施工、审查、验证、退回和持续运行由工作流与调度机制组织。前期 AI 只需要简单配置，不另建独立 Agent 自主循环体系。

当前阶段先确定功能职责、数据与共用机制、源码目录；暂不映射或搬迁旧 WEXPC 代码。

## 2. 源码目录草案

以下是应用源代码的维护布局，不是安装目录或运行时用户数据目录。目录不等于进程、编译包或运行时插件。

```text
WEXPC/
├── app/                         # 程序启动、窗口生命周期、功能装配
│
├── UI/                          # WEX 内置界面
│   ├── main.*                   # 主 UI：导航、加载页面、挂载模块面板
│   ├── conversation/            # 对话页
│   │   └── page.*               # 页面及自身的弹窗、局部交互
│   ├── space/                   # Space／Context 页
│   │   └── page.*
│   ├── settings/                # 配置页
│   │   └── page.*
│   └── components/              # 确实共用的控件，按需添加
│
├── space/                       # Space、Group、Context 的组织与关联
├── conversations/               # 对话、消息历史、追加与修改重发
├── AI/                          # 简单 AI 配置：名称、模型、提示设定
│
├── connections/                 # 公共连接与能力
│   ├── api/                     # API 配置与协议适配
│   │   └── UI/                  # 模块专属面板，按需设置
│   ├── github/                  # GitHub 能力
│   │   └── UI/
│   └── local/                   # 本地文件、终端、Git
│
├── workflows/                   # 工作流与调度
│   ├── runtime/                 # 派发、等待、退回、继续及运行记录
│   └── modes/                   # 可复用的工作流模式
│       └── software-development/
│           ├── preset.*         # 软件开发流程与默认配置
│           ├── structure.*      # 需求、架构、代码等关联数据
│           └── UI/              # 模式专属视图，由主界面挂载
│
├── shared/                      # 共用机制，按需细分
│   ├── permissions/             # 授权检查
│   ├── storage/                 # 数据保存基础能力
│   └── credentials/             # 凭证保管
│
├── docs/                        # 设计与工程说明
└── tools/                       # 开发及检查工具
```

说明：
- 用户明确采用 `space/`，不使用 `workspace/`；采用大写 `AI/`，不使用 `agents/`。
- `.*` 是后缀占位，不是已确定的文件格式或语言。
- 子目录按实际需要创建，不一次性生成空壳。
- 前期不独立设置 `work/`、`templates/`、`dispatcher/`、`execution/` 顶层目录。必要行为归入工作流、连接或共用机制，不因此删除授权、真实回执、结果未知等保障。
- 对话可以独立调用模型，不强制经过 Context 或工作流。
- 工作流可包含循环、条件和退回；调度器按规则推动，AI 和工具执行具体工作。
- 软件开发模式的需求、架构、代码关系和视图就近维护，不另建需求管理、架构管理或项目管理平台。
- `shared/` 只容纳实际共用机制，不接管所有业务状态，不作为杂物目录。
- 每个实际维护单元就近记录职责、修改位置、依赖与验证方法，例如使用 `MODULE.md`。

## 3. UI 组织规则

### 3.1 内置页面集中维护

主 UI 负责界面框架、导航、页面加载和模块面板挂载。按实际页面划分目录，不按底层每个功能划分一个页面。

前期以对话、Space／Context、配置页面为例；页面数量并未冻结。AI、连接等配置可以呈现在配置页或弹窗中，不必各自新建独立页面。

页面自身的小弹窗、按钮和局部交互先留在页面文件内。复杂后才在同目录拆分，不强制配齐 controller、service、hooks 等文件。确实跨页面共用的控件才提取到 `UI/components/`。

### 3.2 可接入模块携带专属 UI

连接器、插件或工作流模式有专属面板时，将面板放在模块内部。WEX 的主 UI 或相应页面负责挂载；模块维护面板自己的配置和交互。

没有专属交互的模块不需要 UI；简单配置可以由统一表单机制呈现，具体实现后定。不得给每个功能目录机械建立 UI 子目录。

修改页面布局和局部交互应主要留在该页面目录；修改模块专属面板应主要留在该模块。涉及业务规则变化时，仍需修改相应业务实现，不承诺所有改动只动一个文件。

### 3.3 加载目标与源码目录分开

运行时加入扩展并重新加载使用，仍是设计目标。源码中存在模块目录，不代表已安装的 WEX 可以直接执行任意源码目录。扩展包格式、构建和加载机制需要后续结合技术栈验证。

## 4. 数据归属与文件存放不是一回事

对话维护消息，连接维护连接配置，工作流维护任务、流程与运行记录，Space／Context 维护组织和关联。它们可以共用存储基础能力，但不混淆业务归属。

业务数据归某个模块，不表示数据写进该模块的源码目录或安装目录。实际持久化位置按数据种类区分：公共配置和登记信息位于用户选择的 WEX 公共数据根目录；Space 工作区和独立 Context 的实际目录可由用户另行指定，且不强制属于公共数据根目录。详见 [Space 与工作流编辑器设计](WEXPC-SPACE-AND-WORKFLOW-EDITOR-DESIGN-2026-10-30.md)。

## 5. Windows 安装后文件存放要求

核心要求：除系统必须管理的内容外，WEX 自己管理的文件默认放在用户选择的目录内。

安装在 D 盘不天然意味着数据也在 D 盘；实现时必须显式安排路径，不能放任各模块和依赖组件分别使用系统盘默认位置。

| 类别 | 内容 | 要求 |
|---|---|---|
| 程序安装目录 | 主程序、运行依赖、随版本发布的内置资源 | 安装时选择；由安装和更新过程管理 |
| WEX 公共数据根目录 | 软件公共配置、AI/连接公共配置、已登记工作区/Context 的索引、必要应用状态和日志等 | 用户选择；不强制包含各 Space/Context 的实际资料 |
| 后装扩展 | 连接器、插件、面板等扩展包 | 默认放在数据根目录下，与主程序分开 |
| 扩展数据 | 扩展配置、状态和历史 | 与扩展程序包分开，更新扩展不得覆盖 |
| 缓存、日志、可控制的临时文件 | 运行辅助文件 | 默认跟随数据根目录；与正式数据分区组织，便于清理 |
| 系统凭证、注册信息等 | Windows 必须管理的内容 | 允许位于系统管理位置 |
| Space 工作区或独立 Context 目录 | 用户选择的工作区及其资料、Context 自有记录；或独立 Context 目录 | 可以位于任意用户选择的磁盘/路径，接入后不自动搬迁；相关外部资源仍以引用为主 |
| 其他外部资源目录 | 既有代码仓库、小说、研究资料等 | 保持原位置；WEX 引用并按授权访问，不自动迁入 |

安装目录与数据根目录分别选择，可以在同一磁盘，也可以在不同磁盘。具体数据子目录名称暂不冻结。

### 5.1 路径与生命周期

- 模块统一取得数据路径，不各自硬编码 AppData、安装位置或盘符。
- 内嵌网页组件、下载、更新和第三方依赖的缓存及数据位置也需检查，能配置的应遵循用户选择。
- 确实无法遵循的系统或依赖例外，记录用途、位置和原因；不承诺系统盘绝对零写入。
- 主程序升级不得覆盖工作数据；扩展升级不得覆盖扩展数据。
- 卸载默认保留用户数据；删除数据应作为明确的独立选择，外部工作文件不随卸载删除。
- 切换数据根目录需要受控迁移、完整性检查和失败恢复，不能只改路径造成数据失联。
- 保存用于定位数据目录的少量系统信息可以重建；丢失它不应导致已有数据无法再次选择和打开。

## 6. 重装系统／更换系统盘后的恢复要求

目标：数据盘完好时，重装系统后可以重新接回 WEX 数据，而不是从头配置所有工作内容。

预期操作：
1. 重新安装 WEX，或修复必要的运行环境。
2. 选择原有 WEX 数据根目录。
3. 识别数据格式及版本，恢复公共配置、已登记的 Space/Context 路径、可访问的对话和工作流、运行记录及扩展配置；若 Space/Context 位于其他位置，允许重新关联原目录。
4. 检查扩展兼容性；修复发生变化的外部路径。
5. 重新配置失效的凭证，并确认必要的访问授权。
6. 核对中断中的工作后再恢复执行。

约束：
- 数据根目录包含识别自身所需的非秘密元信息，不依赖旧系统盘上唯一的一份索引才能打开。
- 系统凭证可能随旧系统丢失，不能承诺 API Key、登录令牌或旧授权自动恢复。
- 盘符、账号和外部目录可能变化，应允许重新定位。
- 保留中断记录；结果未知的操作不能因为重装后恢复工作流就自动重复执行。
- 打开已有数据时先检查版本兼容，不能静默清空或覆盖；必要迁移应可恢复。
- 以上是恢复目标，尚未进行安装、重装或故障测试。

D 盘不等于备份。如果 C、D 是同一物理硬盘的分区，整盘故障仍可能同时丢失。该安排解决系统重装和系统盘更换后的数据接回，不替代独立备份。

技术栈与安装方案明确后，再验证：
- 安装位置与数据位置分别选择，升级后数据保留。
- 主要写入遵循数据根目录，系统位置例外可追踪。
- 扩展包更新与扩展数据隔离。
- 新系统安装后选择旧数据目录可恢复；缺失凭证和路径有明确处理。
- 中断／结果未知的工作不会被盲目重放。

## 9. 2026-10-30 确认的 Electron + TypeScript 落地影响

- **语言与桌面宿主**：WEXPC1 新实现优先使用 TypeScript 单主语言、Electron 桌面宿主、React UI；基础工作流编辑使用 React Flow。不是已经打包或运行成功的声明。旧 Rust/Tauri 源码可选择性借鉴行为与测试，不强制复用其耦合结构。
- **保留既有功能域目录**：`app/`、`UI/`、`space/`、`conversations/`、`AI/`、`connections/`、`workflows/`、`shared/` 仍然代表职责与修改局部性，不强制每个域对应一个 Electron 进程或编译包。仅在 `app/` 中组织必要 Electron 主进程、preload、渲染入口及后台工作进程接线；具体文件和签名以实现为准。
- **受控桌面边界**：renderer 只运行 UI，保持 `contextIsolation`、`sandbox` 等安全默认值，不启用 renderer `nodeIntegration`；preload 仅暴露业务所需的受限接口，主进程必须验证 IPC 来源、参数和实际授权。长运行或可能阻塞的任务使用独立工作进程候选，不把全部业务塞进 Electron main。
- **DSH 外部连接器**：`connections/` 下首期增加 DSH 适配能力；通过 DSH 可用公开接口发送任务、接收可获取的回执与产物引用。DSH 独立运行，不要求客户端嵌入、Cordis 先行接入、完整内部状态同步或自动审查。基本任务交接先可人工验收。
- **工作流**：React Flow 负责首期核心节点/连线编辑与保存；编辑和运行分开。流程可在初期仅负责简单任务交接、人工验收与返工，后续深化调度，不将基础画布重新列为独立自研项目。
- **Cordis**：是 WEX 长期插件管理及 DSH 插件生态的重要首选候选，不作为首期 DSH 连接器运行前置；不默认宣称所有 DSH 插件可直接安装。
- **安装与存储**：Electron 默认 `userData`、`sessionData` 路径须由启动逻辑明确初始化并控制，尤其 `sessionData` 需要在 `app.ready` 前调整；不得依赖安装在 D 盘就自动把浏览器缓存、应用配置移到 D 盘。选择原有用户数据目录与恢复逻辑必须不依赖旧系统盘唯一索引。Windows 系统凭证及无法重定向的系统文件仍为例外。
- **打包**：Electron Forge 为优先候选，不视作已经满足安装目录选择、数据根目录迁移、升级保留和卸载默认留数据要求；安装器行为单独验收。
- **轻量目标**：优先降低代码维护与接入复杂度，不承诺 Electron 的包体或内存比 Tauri 更小；应限制同时运行的 Agent/工作进程、清理历史缓存及释放 UI 订阅。
- **版本边界**：不据此改 WEXPC 主仓 0.1.1 / 0.1.2 正式排期，不删除长期需求，不自动迁移源码；先完成独立 WEX UI + Context + 任务卡 + React Flow + DSH 连接器的可用闭环。

## 10. 目录补充：权限、角色与账号（2026-10-30）

按用户新确认的职责边界，新增独立顶层 `permissions/`（权限策略、授权决策及撤权，原草案 `shared/permissions/` 不再作为业务实现目录）；`AI/roles/` 单独存放 AI 角色配置，AI 目录未来按实际需要扩展记忆等功能；`accounts/` 仅预留未来账号与身份体系研究入口。身份、角色配置、有效授权分别属于不同业务，不互相代替。首版不以 WEX 账户登录为启动前置。现有 §2 目录树是早期草案，应以仓库 README 的最新目录索引及这节补充为准。
