# ADR-0001：按完整功能模块与公共机制组织仓库

- 日期：2026-10-28
- 状态：已接受（架构研究阶段）
- 影响面：仓库目录、依赖方向、编码规范、AI 施工流程

## 1. 背景与问题

WEX 的功能会长期增加：连接器、工作流、Agent、协作方式、外部服务、设备。当前常见的组织方式存在两类问题：

1. **按技术层组织**（core / service / host / network / auth / storage）：给某个连接器加一个功能，需要同时改多个位置，功能责任不完整，长期维护与 AI 施工成本高。
2. **按 UI 页面组织**（软件开发页、小说页、对话页）：把页面当成了底层模块，导致每个模式重复实现 Agent、工具、权限、执行。

我们需要一套组织方式，使：

- 一个完整功能模块可以独立理解、修改、测试；
- 公共机制可以复用，但不吞并业务；
- UI 与底层通过清晰接口交互，不互相绑定；
- 新增功能尽量局部完成，不大量修改中央代码；
- 适合多个 AI 并行施工和长期维护。

## 2. 选项

### 选项 A：继续技术分层

- 做法：core / service / host / adapters 分层，连接器逻辑分散在各层。
- 优点：团队熟悉、上手快、早期结构简单。
- 代价：功能扩散；中央 core 逐渐知道所有业务；新增连接器需改多处；AI 难以独立维护单模块。
- 风险：半年后重构成本更高。

### 选项 B：动态插件架构

- 做法：每个能力是独立插件，定义 ABI、动态加载、版本矩阵。
- 优点：隔离强、可第三方扩展、可热更新。
- 代价：ABI/序列化/安全/调试/版本管理成本高；第一方模块也要背插件复杂度。
- 风险：产品早期把成本花在生态上，功能交付被拖慢。

### 选项 C：完整功能模块 + 公共机制（本 ADR 选择）

- 做法：
  - `apps/`：可交付程序，组合根 + IPC；
  - `modules/`：第一方完整功能模块（连接器、领域模块）；
  - `platform/`：公共机制（契约、注册、调用、权限、账本、存储、凭证、事件、宿主）；
  - `tools/`：架构护栏。
  - 模块只依赖契约与平台接口；平台不依赖业务；模块之间只通过能力调用/事件/契约 DTO 通信。
- 优点：
  - 功能责任完整，新增能力局部完成；
  - 公共机制可复用且不吞业务；
  - 目录即边界，AI 可按模块独立施工；
  - 不引入动态插件复杂度，未来可按需升级。
- 代价：
  - 前期需要契约、模板、工具投入；
  - 每个模块多几个文件；
  - 需要持续维护依赖检查，否则边界会腐化。
- 风险：过度设计（连接器少时收益低）、契约频繁变更、团队不遵守规则。

## 3. 决定

采用选项 C。

具体规则：

1. 一级目录：`apps/`、`modules/`、`platform/`、`tools/`、`docs/`。
2. `modules/` 平铺，不套分类层。
3. `platform/` 只放多模块共享且语义一致的机制，不允许出现业务词。
4. 模块公开面最小化；模块内部自由组织，不机械递归。
5. 依赖方向：`modules → contract/platform trait`；`platform → contract`；`apps → all`；禁止反向与循环。
6. 用 `arch-check`、契约测试、模块模板强制执行，不靠自觉。
7. 现有代码按“复用/适配/替换/仅参考”逐项迁移，不一次性重写。

## 4. 影响

- 目录：按 `01-repository-structure.md` 调整。
- 依赖：按 `04-dependency-rules.md` 执行，CI 检查。
- 契约：新增 `platform/contract`，版本化。
- 数据：模块自带迁移，平台汇总。
- UI：只依赖 IPC 生成类型；按交互集合分 features。
- 测试：模块契约/单元/回放 + 应用集成。
- 迁移：按 `06-migration.md` 分阶段，先试点。

## 5. 退出条件 / 复查触发

出现以下任一情况，重新评估本 ADR：

- 连接器长期少于 3 个，且没有第二个工作模式；
- 维护者只有 1 人 + 1 AI，且模块化开销明显大于收益；
- 契约变更频率高于模块变更频率（说明抽象不稳定）；
- 动态插件/第三方生态成为明确产品需求；
- Tauri/React 技术路线被证伪，需要更换 UI 技术（后端结构应仍成立，但需复查 apps 层）。
