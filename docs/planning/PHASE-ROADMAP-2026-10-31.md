## 1. 规划目标

把 WEX 从“架构、契约和基础机制已具备首轮成果”推进到真正可安装、可运行、可持续使用的 Windows 桌面产品。

首版目标不是做一个能展示页面的聊天壳，而是让用户能够：

1. 安装并启动 Windows 版 WEX，选择程序安装位置和持久数据位置。
2. 建立 Space / Group / Context，独立使用普通对话；Context 可以自由组合角色、资料、连接和工作能力。
3. 配置 API Provider、模型及凭证，进行可恢复的普通对话。
4. 在授权范围内访问本地文件、终端、Git 和 GitHub，获得真实操作回执与可核验产物。
5. 建立可持久化的工作流和任务，配置不同 Agent/职责，分派、追踪、审查、验证和接续工作。
6. 至少完成一条真实的软件开发工作模式 V1 闭环，能够用于继续开发 WEX 的 PC 与 Android 项目。
7. 中断或重启后先核对真实资源与未知操作，再恢复未完成工作；不能盲目重放副作用。
8. 查看必要的连接状态、任务状态、操作回执、日志和诊断；数据可以备份、恢复和重新接入。

产品范围以正式 WEXPC 基线和用户已确认要求为准。本路线只安排实现顺序，不缩减 0.1.1 已确认的本地工具、多 Agent、独立审查/验证和持续接续要求。

- 收尾条件：第七批最终修复在当前环境重新运行完整测试；Electron 兼容性另行验证。

| 阶段 | 目标 | 核心模块 | 进入下一阶段的条件 |

| 2. 工作空间与角色 | 建立通用组织对象和可复用 AI 配置 | space、AI/roles、views | Context 独立存在、多处引用不复制；角色/职责/模型/授权分离；布局不拥有业务状态 |
| 3. 对话与 API | 形成独立普通对话和真实模型连接 | conversations、connections/api、shared/credentials | 无 Context/Task 也可聊天；消息历史、段落版本、追加/修改重发可恢复；真实 Provider 请求与凭证边界通过 |
| 4. 本地与远端连接 | 让受控能力作用于真实资源 | connections/local、connections/github、permissions | 文件/终端/Git/GitHub 的真实调用、授权、回执、unknown 与回读核验可区分；无越权和盲重试 |
| 5. 工作流与调度 | 建立任务、运行、资源协调和恢复机制 | workflows、connections、permissions、shared | Task 与 Operation 分属正确 owner；能处理并发冲突、撤权、超时、未知结果、重启恢复；不依赖 UI 保存权威状态 |
| 6. 外部 Agent 接入 | 让外部执行者成为可替换的连接目标 | connections/dsh、app、workflows | 固定版本 DSH 的真实成功/失败/接收状态/产物定位得到证据；外部 Session 不被 WEX 镜像或接管 |
| 7. 产品交互与软件开发模式 V1 | 把已实现的领域能力组成用户可操作产品 | UI、views、workflows/editor、workflows/modes/software-development | 普通聊天和无模板 Context 仍可用；软件开发模板可选；工作流编辑修订可保存；真实任务/Agent/证据可查看和操作 |

## 4. 首版范围与后置范围

### 首版必须实现或达到可验收状态

- Windows 桌面宿主、基本导航和设置入口。
- Space / 可选 Group / 通用 Context；Context 与项目、资料、连接、角色和会话关系可组合。
- AI 基础配置、角色与职责分离；不要求完整长期记忆系统。
- 独立普通对话、API Provider/Model 配置、消息历史及必要的编辑/追加/重发交互。
- 本地文件、终端、Git，以及按能力边界逐项实现的 GitHub 连接。
- 三层权限和真实操作前复核；角色、Context、模板或连接选择均不能自动扩权。
- 持久化工作流定义、Task、Agent 分派、操作关联、产物、独立 Review/Verification 和恢复入口。
- 至少两个可区分的执行身份在不重叠资源范围内真实施工；重叠写入必须被阻止或串行化，不能仅靠提示词约束。
- 软件开发模式 V1：可组织需求/功能层级、关联任务、Agent、Context 与真实代码资源；提供基础树形/关联视图和工作流编辑器。
- 外部 Agent 连接能力按真实接口逐项实现；DSH 是优先适配目标，但不是原生聊天和本地工具的唯一前置。
- 数据位置、日志/诊断、备份恢复、升级/卸载及重装后重新配置凭证和授权的完整用户行为。

### 不作为首版阻塞项

- 完整自由画布、多专业视图和复杂可视化编辑。
- WEX 自有通用动态插件平台及插件市场。
- 将 DSH Core/Loader 或 Hermes Agent 运行时搬进 WEX；DSH 原生 Bundle 宿主兼容实验与外部 Agent 连接器是两条不同路线。
- 账号体系、云端空间、跨设备协同、社交平台、学习网站、能力市场和公开项目生态。
- 公共知识库、公共策略库、完整角色长期记忆和自主演化体系。
- 浏览器自动化、复杂抓取、小说等其他专业模式。
- 无条件后台常驻、开机自启、应用关闭/电脑休眠后仍保证执行。

这些能力保留长期需求或研究位置，不因本路线图而删除，也不自动并入首版。

## 5. 关键架构约束

1. WEX 是联通、调度、交互和结果管理宿主，不重建一套与 DSH/Hermes 等外部 Agent 重复的完整执行平台。
2. WEX 自有 API、文件、终端、Git/GitHub 等连接能力保持独立可用；外部 Agent 是可选连接器和执行目标。
3. DSH Agent 连接器（`connections/dsh/`）与 DSH 原生插件宿主研究（`dsh/`）严格分开；二者不能互相代替验收。
4. Task / Workflow 的正式状态归 `workflows`；Operation / attempt / 外部调用回执归 `connections`；权限决策归 `permissions`；shared 只提供技术机制；UI/views 只呈现和提交用户意图。
5. Context、角色、连接、资源的关联不代表授权；实际动作仍需由可信宿主和权限模块校验。
6. 外部 Agent 的内部 Session 和工具历史由外部客户端维护；WEX 保存自己的派发事实、会话定位、接收状态、产物引用及独立核验。
7. 对外部副作用不承诺 exactly-once。结果未知时先查询/核对真实资源，不盲目重派。
8. Windows 数据根、Space 工作区、独立 Context 目录、外部资源和程序安装目录分开管理；重装后可重新接回普通数据，但凭证和有效授权不得自动恢复。

## 6. 验收证据门槛

| 等级 | 证据 | 能证明什么 |
|---|---|---|
| E0 | 文档、契约和静态推演 | 责任、语义和边界已被说明 |
| E1 | 替身/故障夹具 | 指定模块行为和失败语义 |
| E2 | 真实本地进程、文件、数据库和重启 | 本机技术机制和持久化行为 |
| E3 | 获授权的真实外部服务、Agent 或插件 | 真实外部交互和回执 |
| E4 | Windows Electron 安装、窗口、ACL、凭证、升级/卸载/重装 | 实际桌面平台使用与恢复 |

每项验收写明实际达到的最高等级和缺失证据。E0/E1 不能替代 E2–E4；Linux Electron 冒烟不能冒充 Windows 实机通过。

## 7. 阶段控制规则

- 不按业务链路拆模块施工；按 owner 模块实施，复杂链路用于跨模块组合验收。
- 每阶段进入时读取最新 main、对应模块契约、当前决策和已有测试。
- 稳定能力先施工；B 候选保持可替换，C 待实验，D 待用户决定。不得用工程便利擅自关闭 D。
- 不提前冻结所有接口；以真实提供者和消费者的最小共同语义逐步收敛。
- 每阶段完成前更新 owner 契约、全局索引、验收证据和下一阶段任务。
- 默认 main 小批量提交；不为普通改动建分支，不创建无必要 PR。
- 不触发 GitHub Actions；本地或可用云端环境验证。若环境缺失，记录阻塞和可复现命令，不伪造通过。
- 施工批次不设日历承诺。按依赖和验收推进，不以估算日期替代证据。
