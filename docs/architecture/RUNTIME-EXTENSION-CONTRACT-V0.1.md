# WEXPC 运行时扩展接入契约 V0.1

- 日期：2026-10-28
- 状态：工程候选方案，待讨论与试点验证；不是已冻结签名、ABI 或已实现功能。
- 上位设计：[按功能聚合的目录与模块设计](MODULE-LOCALITY-DESIGN-V0.1.md)。
- 已确认目标：添加新模块后无需退出、重建或重装 WEX；加载后能力及相关 UI 可用。
- 本稿只规定语言无关的接入语义。字段名为示意，序列化、运行时、隔离和构建方案未定。不修改产品代码，不启动外部服务。
- 不保证每个模块都可以动态替换。先验证模型协议与配置面板；数据库底座、权限核心等能否热换另行决定。

## 1. 一个维护模块、一个发布包、多个接入面

源码目录按完整功能聚合；可安装扩展是其发布产物，两者不必逐目录一一对应。

一个扩展包可以同时贡献后端能力、配置面板和模板视图，用户一次安装，不要求分别找两个包。包内前端与后端仍有独立入口和版本兼容检查，不能因为同包就让浏览器直接访问后端内存或秘密。

建议区分：
- package_id / package_version：扩展包身份与版本。
- instance_id：加载实例；允许同一实现服务多个配置实例。
- connection_id：用户连接身份；升级实现不应改变账号与历史引用。
- capability_id / capability_version：公开能力。
- activation_id：本次激活代次；旧请求不能在重载后静默转向新实现。

这些身份不能互相替代。包版本升级不等于接口发生破坏性变化；兼容的接口也不代表其所有数据格式都兼容。

## 2. 最小包清单

清单由宿主在执行扩展代码之前读取。建议字段如下：

| 项目 | 用途 |
|---|---|
| 包 ID、版本、说明 | 识别扩展及展示 |
| 宿主扩展契约兼容范围 | 判断当前 WEX 能否加载 |
| 后端入口、UI 入口及各自运行格式 | 加载对应发布产物，不推测源码语言 |
| 所需服务及契约版本 | 例如模型注册、配置、受控网络、凭证使用、UI 插槽 |
| 提供的能力／服务／面板 ID | 检查重复与所有权 |
| 配置 schema 与数据版本 | 配置校验及升级判断 |
| 所需权限声明 | 只表达需要，不授予权限 |
| 停用与迁移支持信息 | 说明限制，不能冒充宿主验证结果 |

具体 JSON/TOML 格式待定。机器清单与运行时注册内容应相互校验或由同一来源生成；MODULE.md 解释边界与施工方式，不重复维护全部字段。

模块目录或发布包若存在未写完的文件，不能边复制边激活。候选做法是暂存后检查、一次发布完整版本；具体完成标志与文件校验方式由加载方案决定。安装目录与开发源码目录分别处理。

## 3. 模型适配契约

### 3.1 三方职责

| 参与方 | 责任 |
|---|---|
| API 模块的模型契约 | 统一生成输入、事件、完成与错误语义 |
| 协议扩展 | 请求转换、协议解析、厂商错误与参数支持映射 |
| Conversation／Agent 工作循环 | 构造上下文、消费输出、将工具意图交执行服务 |

聊天与工具回合不能导入具体协议实现。协议扩展不能自行执行工具、批准权限或把 Task 标记完成。

建议入口语义：查询模型支持信息、开始生成、请求取消、等待生成结束。最终采用函数、消息协议或异步流尚未决定。

### 3.2 生成输入

最少包含请求身份、连接与配置修订、适配器激活代次、模型标识、有序消息、可用工具声明、生成参数、取消与期限关联。普通调用不强制 Task 或项目。

凭证通过宿主规定的受控方式使用，不置于普通配置、消息或事件。究竟提供受控请求服务、短时秘密句柄还是受限执行环境，须结合运行时选型；不能仅凭“句柄”声称扩展无法外泄。

开始时固定本次连接／模型／配置与实现版本。之后修改设置仅影响后续调用，不偷换在途请求的账号、地址或模型。

### 3.3 输出与结束

- 增量文本和工具参数片段是临时展示数据。
- 完整工具提议必须在参数及结束状态核验后发布，不能执行半截参数。
- 每次生成只能结算一次成功、失败或取消终态；EOF／断线不是成功证明。
- 用量可以未知，不补造 0；厂商特有续传数据携带版本及适用绑定，不作为通用可显示文本。
- 不支持的参数明确报错或在调用前明确协商降级，不能静默丢弃。
- 重复事件、序列缺口、终态后事件由公共消费端识别；最大消息、缓冲和背压标准需定义。
- 取消生成与取消已执行工具分开；错误不得暗中重发可能产生副作用的操作。
- 流式与非流式共用完成与错误语义，不维护两套厂商判断分支。

### 3.4 验证

同一套契约测试供不同适配器使用，覆盖文本、完整工具意图、分片、错误终态、取消、未知用量、不支持参数和配置隔离。通过协议测试不等于真实厂商可用；模拟、真实服务和桌面接入分别记录。

## 4. UI 插槽契约

### 4.1 首批候选插槽

| 插槽 | 贡献内容 | 宿主提供 |
|---|---|---|
| connection.settings | 连接专属配置面板 | connection_id、修订、配置读取／提交入口 |
| context.workspace | 模板专属工作视图 | context_id、所引用对象的受控查询与命令 |
| navigation.page | 独立页面入口 | 路由身份、导航服务、启停状态 |
| operation.result | 操作结果专属展示 | 有版本的结果投影、受控产物读取 |

首个试点只需要 connection.settings；不先建设所有插槽。

每项贡献声明 ID、插槽类型、契约版本、组件入口与适用条件。宿主负责稳定排序、冲突报告和生命周期，不能靠加载先后覆盖同名项。

### 4.2 面板权限与状态

面板拿受控客户端，不直接接数据库、凭证或连接器内部实现。UI 的本地校验用于交互，Host 再校验输入及当前权限。扩展 UI 代码不能因为挂在设置页就获得全部设置管理权。

简单面板可在一个文件中包含布局、按钮、草稿和请求，不强制拆层。面板只能引用公开控件／服务，不引用其他模块的内部组件。

草稿应绑定对象和修订。重载前若有未保存内容，采用保留、确认丢弃或阻止重载的明确策略，不静默清空。具体选择按面板契约细化。

宿主可在新注册表发布后更新受影响面板，不要求刷新整个窗口；用户入口可统一称“重新加载扩展”。局部更新还是整页刷新为待验证实现，不保证现有代码已支持。

### 4.3 失败与退出

加载失败展示错误并保留其他模块可用；UI 错误边界不等于进程或安全隔离。停用后移除入口、清理订阅，历史结果仍可用通用展示器查看，不能因专属渲染器消失而丢失证据。

UI 与后端必须使用兼容的激活代次。请求若来自已过期面板，应拒绝或提示刷新，不静默交给语义不同的新处理器。

## 5. 依赖、注册和激活

### 5.1 允许依赖

- 模块可依赖公共契约、所声明服务和合法实现库。
- UI／模板可调用公开客户端和复用组件，不能穿透模块内部。
- 通用宿主不导入具体扩展业务；唯一装配入口负责发现和绑定。
- 模板使用通用工作、连接和执行接口，不复制其权威状态。
- 加载器检查必需依赖、接口版本、循环和重复 ID；可选依赖缺失需要声明降级行为。

### 5.2 激活流程

发现 → 读取清单 → 检查完整性／兼容／依赖 → 准备实例 → 暂存注册 → 发布激活代次 → 通知 UI。

激活前不得进入实际业务调用。后端与 UI 任一必需部分准备失败，就撤销暂存注册并清理资源；不能对外呈现一半可用的功能。无 UI 的扩展可声明无需面板。

注册表持有“谁提供什么”，业务模块持有自己的实现与状态。消费者按公开 ID／接口解析，不能缓存无生命周期管理的内部引用。

“事务式发布”是注册可见性的目标，不表示跨进程、网络和数据库天然存在一个原子事务。具体故障恢复需在实现方案中验证。

## 6. 停用、更新与恢复

候选状态：已发现、待检查、准备中、已启用、停止接收、等待在途结束、已停用、失败／不兼容。未激活包不自动运行初始化脚本。

停用顺序：
1. 关闭新调用准入，并处理或阻止相关排队项继续投递。
2. 保留已准入调用绑定；等待完成，或按支持能力请求取消。
3. 保存已知结果或结果未知事实，不能把超时记成未执行。
4. 清理面板、订阅、后台任务和注册。
5. 释放运行资源；配置、历史与回执不默认删除。

首阶段默认不允许有在途工作的实现被强制替换。需要强制停止时必须明确结果未知及恢复路径；不是一个隐藏“忽略占用”开关。

更新候选流程：旁路检查新包 → 停止旧版接收 → 排空 → 校验数据兼容 → 激活新版。检查失败保留旧版；一旦新版已写入不兼容数据，就不能声称可直接回滚旧代码。

依赖服务停用时，依赖者应先停止接收或降级，不留悬空服务。具体依赖生命周期策略待试点。

WEX 重启后恢复已确认配置及历史事实，重新检查扩展兼容性；发现目录不等于自动信任新扩展。重装后凭证和授权仍须重新建立。

## 7. 数据与状态 owner（候选）

| 信息 | 权威 owner |
|---|---|
| 扩展包与激活状态 | 扩展宿主 |
| 连接实例与配置修订 | connections/catalog |
| 模型本次生成状态 | 会话生成协调入口；与 Agent Loop 的边界待细化 |
| 任务目标、验收与正式状态 | work |
| 队列、派发尝试、领取与占用 | dispatcher |
| 单次操作、执行结果及回执关联 | execution |
| 授权、审批和撤销 | permissions |
| 面板草稿与选中态 | 对应 UI 实例 |

派发尝试与操作执行尝试须使用不同概念／标识，不因为都叫 attempt 就共用一条状态。本文不冻结表结构。

## 8. 对目录设计的直接影响

- 每个可安装维护单元需要发布清单与明确入口，模块说明跟源码走。
- 同一模块可含 UI 与后端发布产物，但不意味着共享运行上下文。
- 扩展宿主暂归 apps/desktop 的装配职责；复杂后是否独立目录待定，不再新增一套业务执行服务。
- 协议接口留在 API 功能域；UI 插槽接口留在 UI 宿主域；加载清单和生命周期接口由扩展宿主管理。仅跨域必要语义进入公共契约。
- 不把所有接口都塞入 platform/contract；更不因插件化把所有内部文件独立成包。

## 9. 试点规格与下一步

本稿定义试点规格，尚未启动实现。

固定一个已构建宿主，添加构建时未知的协议扩展和设置面板。验证发现、检查、激活、真实请求、取消、停用、重复 ID、缺失依赖、失败清理和旧数据保留。对比改动清单，确认没有新增中央厂商分支。

工程检查还应覆盖跨模块内部引用、清单与注册一致性、模块说明存在与接口变更同步。diff 文件数量用于诊断，不设迫使隐藏改动或删测试的死上限。

下一决策：比较能够同时承载后端扩展与 UI 贡献的运行方案，并做最小加载验证。未选语言、未冻结 ABI；没有证据前不决定全仓换语言，也不把现有 Rust 代码永久锁定。
