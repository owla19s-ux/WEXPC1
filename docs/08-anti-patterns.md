# 08 — 反模式清单

> 本文列出会把架构拖回旧状态的做法。每条给：症状、原因、正确做法。

## 一、任务书明确点名的九种

### 1. 把 UI 功能等同于底层模块

**症状**：出现 `modules/software-dev`、`modules/novel-mode`、`modules/conversation-engine`。

**原因**：把“页面”当成了“功能单元”。

**正确做法**：UI 是 `apps/ui/features/*`；底层是能力模块 + 工作流模板。软件开发 = 工作流模板组合 github/git/terminal/localfs，不是一个模块。

### 2. 把所有技术共性拆成独立一级系统

**症状**：`network/`、`auth/`、`storage/`、`logging/`、`permission/`、`dispatch/` 各自一级目录，GitHub 功能散落其中。

**原因**：按“技术关注点”而不是“功能完整性”切。

**正确做法**：技术共性进 `platform/`（只放多模块共享且语义一致的机制）；其余留在各模块内部。

### 3. 创建巨大中央 Core

**症状**：`core/` 越来越大，所有模块依赖它，它知道所有业务。

**原因**：把“共享”误解为“集中”。

**正确做法**：中央只有机制；机制无业务词；领域/能力各自拥有业务。

### 4. 机械递归

**症状**：每个小模块都拆 `common/`、`internal/`、`submodules/`，目录比代码多。

**原因**：把“分级组织”误解为“每级都要有相同结构”。

**正确做法**：拆分判据（5 条，满足 2 条才拆）；模块内部按真实复杂度组织。

### 5. 将关联等同于权限

**症状**：Context 关联 GitHub 仓库后，AI 自动获得写权限；或组织移动继承权限。

**原因**：把“引用关系”实现成“所有权/授权”。

**正确做法**：关联只表达引用；权限在执行点按主体/动作/资源/审批判定；组织关系不产生授权。

### 6. 让工作流模板写死业务结构

**症状**：软件开发工作流变成所有 Context 的标准模型；模板里出现 `if`/脚本；模板能定义新步骤类型。

**原因**：把“可编辑”误解为“可编程”。

**正确做法**：模板是版本化配置；固定步骤枚举；模板/实例分离；新增步骤类型走契约变更。

### 7. 提前规定物理目录

**症状**：还没定职责就画完整代码树，然后为了填满目录造空壳。

**原因**：把目录当起点。

**正确做法**：先定责任/依赖/契约，再定目录；目录是结果。

### 8. 重命名传统架构

**症状**：Core 改名 Runtime/Foundation，分层没变，就宣称新架构。

**原因**：换词不换结构。

**正确做法**：按依赖方向与职责重新归属；说明解决了什么真实问题；不新造名词。

### 9. 把候选当已确认

**症状**：文档里写“将采用”“建议”，代码/评审却当成已批准；实验没做就冻结接口。

**原因**：混淆“讨论/候选/已确认/已实现/已验证”。

**正确做法**：状态分级；实验通过才升级；ADR 记录。

## 二、本方案特有的反模式

### 10. 平台机制吞业务

**症状**：`policy` 里出现 `match connector == "github"`；`ledger` 里出现 issue 字段；`invoke` 里知道文件路径规则。

**原因**：为了“统一”把模块逻辑上移。

**正确做法**：机制只做组合/记录/分发；具体规则由模块注册或模块内部实现。

### 11. 模块之间直接 import

**症状**：`ai-api` 直接 `use github::api::...`；两个模块共享一个内部 struct。

**原因**：短期方便。

**正确做法**：能力调用、事件、或把 DTO 上移 contract。

### 12. 全局配置大对象

**症状**：`AppConfig` 包含所有连接器字段，每加一个连接器就加字段，所有模块都依赖它。

**原因**：把“配置”当成“一个对象”。

**正确做法**：应用级/模块级/实例级分层；模块自己解析自己的段。

### 13. 中央注册表 + match

**症状**：新增连接器要改 `registry.rs`、`dispatch.rs`、`tools.rs` 三处 match。

**原因**：用中央代码表达开放集合。

**正确做法**：稳定 ID + descriptor + 分布式注册；中央不写 match。

### 14. 双写状态

**症状**：Rust 和 UI 都保存组织数据；两边都能改；靠“同步”保持一致。

**原因**：迁移期遗留，或为了 UI 性能。

**正确做法**：单一写入口；UI 只持投影；事件失效缓存。

### 15. 用 UI 判断权限

**症状**：按钮灰掉就算权限控制；后端无检查；脚本/IPC 可绕过。

**原因**：把体验当安全。

**正确做法**：UI 预检 + 执行点强制检查。

### 16. 先发请求后记账

**症状**：写操作成功后才写数据库；崩溃后重复执行。

**原因**：没意识到副作用先于记录。

**正确做法**：先持久化 InFlight，再发请求；未知不重试。

### 17. 把“能编译/测试绿”当成架构正确

**症状**：CI 全绿，但新增功能改了 8 个中央文件；没人做局部性实验。

**原因**：只验证功能，不验证边界。

**正确做法**：把局部性/删除/并行实验纳入季度检查。

### 18. 文档与代码不同步

**症状**：MODULE.md 说支持 Issue，代码没有；或反之。

**原因**：文档被视为“额外工作”。

**正确做法**：文档是模块的一部分；CI 校验一致性；不同步视为未完成。

### 19. 过度抽象

**症状**：只有一个连接器，却有通用 Connector 框架、插件协议、规则引擎。

**原因**：为未来设计，但没有第二个消费者。

**正确做法**：先有重复再抽公共；机制准入测试；不到阈值用简单结构。

### 20. 保留两套实现

**症状**：新旧路径都在跑，旧路径“以防万一”。

**原因**：不敢删。

**正确做法**：开关切换 + 验证 + 删除；归档而不是并存。

## 三、快速自检表

| 问题 | 如果“是”则危险 |
|---|---|
| 新增功能改了 ≥3 个中央文件？ | 边界可能错了 |
| 平台机制里出现业务词？ | 抽错层 |
| 模块 import 了另一个模块内部？ | 需要改调用方式 |
| UI 保存了业务状态的权威副本？ | 双真相 |
| 权限只在 UI 判断？ | 可绕过 |
| 写操作先发请求后记账？ | 可能重复副作用 |
| 新增连接器要改中央 enum/match？ | 开放集合用错表达 |
| 工作流模板出现脚本/自定义步骤？ | 变成第二套运行时 |
| Context 删除会级联删对象？ | 把关联当所有权 |
| 目录里有空壳占位？ | 架构靠目录证明 |
