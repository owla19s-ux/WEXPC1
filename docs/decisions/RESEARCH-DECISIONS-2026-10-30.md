# WEXPC1 当前研究共识与施工边界（2026-10-30）

> **性质：研究决策摘要与第二批架构细化记录，不是新版本计划或已实现功能声明。** 用这一页汇总最近讨论，减少反复追加同一内容。详细技术证据仍以 [工作流编辑器](../../workflows/editor/README.md)、[DSH 双路线边界](../architecture/DUAL-PLUGIN-SYSTEM-BOUNDARIES-2026-10-30.md)、[DSH 运行报告](../../dsh/README.md) 为准。与先前“首版 WEX 插件采用 Cordis”“编辑器数据可直接作为 WEX 业务数据”的暗示冲突时，以本页最新边界为准。

## 1. 定位与分工

- **WEX 主体**：Space / Group / Context 组织工作、角色、知识与资源；WEX 持有授权、任务/状态、操作回执、跨图关联等业务权威，不以 React Flow、Cordis 或外部 Agent 的内部状态为权威副本。
- **内部连接层 + 公共连接/适配层**：现有连接体系中的两类职责，不新造“插件墙”子系统。内部服务按需接入公共能力边界，外部工具和插件通过受控入口双向交换能力。对外暴露最小授权能力，不交出内部服务实现或完整 Context；真实安全边界另需进程/系统隔离，不能单凭接口限制。
- **内置连接器优先**：WEX 的基础能力通过可独立维护的连接器接入，连接器不承担 Space/Context 组织、调度状态权威或权限账本。现阶段应优先研究 **Agent 客户端连接器**，让外部 Agent 承担复杂执行；API、本地文件/Git、GitHub 等保留为 WEX 的基础操作、独立核验、恢复能力，不追求自建大量重复工具。
- **DSH 两条路线完全不同**：`dsh/` 是内置 Cordis Core+Loader 原生插件兼容实验宿主，目标先达 Windows 真机可加载、执行、卸载并检查真实插件；`connections/dsh/` 连接独立 DSH Agent，目标任务交接与真实回执闭环。两者互不依赖、不共用加载器。WEX 自有插件机制 `plugins/` 仍未定型，不要求首期采用 Cordis 或开发安装市场。

## 2. 工作流编辑器是视图研究，不是数据或执行引擎

- **React Flow = 目前使用的二维图形交互组件**：负责显示、拖拽、连线、选择、缩放和布局。当前 `workflows/editor/prototype/` 的 `model.mjs` 仅是临时草稿模型；不冻结 WEX 的数据结构/节点协议，不作为调度器。
- **WEX 视图引擎是重要的长期架构研究**：业务对象描述“是什么”，专业模板描述“如何理解”，视图表达“如何展示/编辑”；面向软件开发、科研、管理等不同专业场景。相同显示名称（例如“审查”）不保证相同业务语义和运行机制。当前每类一个节点视图文件仅是降低原型修改耦合，不是最终模板节点类型规范。
- **绝大多数架构树/进度节点图不执行**：需求、模块、任务进度、验证等图主要承担组织、理解和状态展示。执行工作流是单独类型；**数据关联 ≠ 执行依赖；映射存在 ≠ 状态必须完全同步**。一个任务阶段变化可让其他图投影不同的进度/待验证状态。
- **多架构树映射方向明确但暂缓实现**：共享稳定对象身份、独立关系映射和视图布局；树内显示编码可以变化，不应作为唯一绑定身份。编辑图时可暂停关联变更传播、隔离草稿，比较修订后发布；不能默认锁死所有其他图或中止运行任务。上述均是设计方向，非现有实现。
- **二维/多视图/三维是可替换呈现方式**：三维仅用于确实帮助理解复杂交叉关系的场景，不预设必须实现；不同图形技术不应决定 WEX 的业务数据。PC 到位后通过真实鼠标、窗口和交互使用研究，而不是现在冻结图层或协议。

## 3. 数据持续性与并发是更难的长期问题

- **难点不是简单节点连线，而是重启、断连、重试、跨 Context、多 Agent 并发后保持可验证的一致性**。WEX 需区分任务意图、调用尝试、外部执行事实、产物、验证和最终验收；结果未知不能冒充失败或成功，防止重复派发产生副作用。
- 编辑器不拥有任务执行，关闭图/切换 Context 不应自动取消既有任务；执行应使用明确版本的工作定义。并发配额、文件资源冲突、恢复策略和后台运行方式留待真实工程验证。
- 规模研究样本：5–15 项目，每项目约五张图，每图 5–20 节点（共 25–75 张图、125–1,500 节点）。这是**总体保存量，不是同时渲染量或并发任务数**。正式性能能力尚未测量；图实例/草稿须分开管理，不把所有项目塞进一个 React State。

## 4. 现阶段做什么 / 不做什么

| 方向 | 当前行动 | 延后到 PC 实测与后续设计 |
|---|---|---|
| React Flow | 保留独立编辑器原型，继续研究简单节点交互、不同展示方式；现有 DOM/模型/构建历史结果可参考 | 正式映射数据层、专业模板执行语义、多图联动、三维、75 图性能实测 |
| DSH 内置插件兼容 | 维护独立 Core+Loader 原型，准备真机对真实插件逐个做装载/依赖/错误验证 | 完整 DSH 服务生态、商店、任意插件兼容承诺 |
| 外部 Agent 连接器 | 优先确认 DSH 等客户端真实可用的交接入口与结果/产物回执；保持与内置插件宿主分离 | 预设不存在的 Agent 控制 API 或全量替代外部执行平台 |
| WEX 基础设施 | 连接器/授权/可持久化任务状态和结果追踪以稳定可检验为目标，复用外部执行能力 | 过早实现 WEX 动态插件平台、统一跨机制底层签名、全套通用图引擎 |

## 5. 验证与协作约束

- **研究样本不等于正式方案**，设计语义可以先确认，实现契约必须等 Windows/Electron 和外部实际连接验证；实验成果逐个纳入，不让单一库绑架主线。
- 第一批 `fb4f7eb` 已重跑节点拆分后的 5 项模型 + 6 项 DOM、TS/Vite 构建和 HTTP 预览，均通过；真实鼠标交互/Electron 仍待 Windows 真机。本批只读既有结果与源码，不把它们当成本次架构的运行证明。
- 仓库目前主要是设计和独立实验，不是已交付 WEX 应用。**不为研究结论批量创建空目录、接口、版本排期或更多重复文档**；尽量更新这份摘要及对应职责文档。
- 不主动触发 GitHub Actions；测试要注明实际执行的命令、环境及未覆盖项。


## 6. 第二批整体职责与依赖方向

审查基线：`a5af22163fcf76eb45302db1703cbd14afec7658`，各源码目录 README、当前研究摘要、Space/Windows 目录要求、已有独立实验及 RDA-001。旧 [WEXPC 基线](https://github.com/owla19s-ux/wexpc/blob/main/docs/PC-PRODUCT-AND-TECH-BASELINE.md) §0/§2.7 仅用于核对 Context 独立、角色/权限分离和可信工作接续；不继承旧 Rust/Tauri 或 project_id 强绑定。

以下为本批**架构责任结论**，允许进入下一轮语义讨论；不表示产品已实现，也不把旧候选接口或实验函数提升为正式协议。AR/S 编号只供文档追踪。

### 模块与依赖

| 领域 | 自己维护的责任 | 允许的协作方向 / 不承担 |
|---|---|---|
| [app](../../app/README.md) | 可信装配、窗口/进程与退出协调、平台隔离承载 | 装配公开入口，不吸收领域业务；领域不反向依赖启动入口 |
| UI / [views](../../views/README.md) | 交互、布局、可重建投影 | 查询/提交到目标领域；不直接写权限、任务或执行结果 |
| [space](../../space/README.md) | Space/Group/Context 本体、放置与组合引用 | 引用其他领域公开对象；不吸收目标的存储、执行与授权 |
| [AI/roles](../../AI/roles/README.md) / [conversations](../../conversations/README.md) | AI 配置/职责关联；独立消息与生成业务 | 使用已选连接与获准资料；不把模型、角色、身份、会话合成一个对象 |
| [workflows](../../workflows/README.md) / runtime | 工作定义、任务、分配/运行、资源协调与恢复、核验验收 | 请求连接能力，依据真实回执推进；不执行厂商协议或直接控制外部内部循环 |
| [workflows/modes](../../workflows/modes/README.md) | 可选组合、专业规则/对象/关系 | 使用通用领域；不复制 Task/权限，不要求 Context 变成软件项目 |
| [connections](../../connections/README.md) 宿主边界 | 连接配置/可用性、统一准入接点、操作尝试/回执 | 调权限、调具体适配器；向外提供注入的最小领域能力，不导入领域私有状态 |
| 具体连接器 / 外部执行方 | 协议、进程/服务调用与可观察证据 | 返回观察，不自行写 Task/权限；外部执行方保有自身会话/执行事实 |
| [permissions](../../permissions/README.md) | 策略、授权/审批/撤销与判定依据 | 被正式调用边界使用，不把组织层级或提示词当授权 |
| [shared](../../shared/README.md) | 存储、凭证等共用技术机制 | 领域定义意义；存储位置不改变 owner，凭证存在不等于使用获准 |
| [dsh](../../dsh/README.md) / [plugins](../../plugins/README.md) | 独立 DSH 插件兼容实验 / 未来 WEX 扩展机制 | 两者不强制承载连接器；不互换加载器，不引入产品级插件框架 |

**双向能力调用不意味着双向源码依赖。** 应用把领域公开入口包装为窄服务，注入受控连接边界；外部回调只拿到获准的能力与本次范围。内部模块的正常局部调用可直接协作；跨外部边界必须核验来源/授权并记录操作事实，目标领域继续检查自身业务规则。这里定依赖责任，不先创建全局协议包或事件总线。

### 数据与状态的唯一权威

| 内容 | 权威维护方 | 引用/派生边界 |
|---|---|---|
| Context 本体、配置与定位；Space/Group 放置关系 | `space`；放置与本体是不同关系 | 多 Space 引用一份本体；公共登记索引只定位，不复制状态 |
| Context 选择的资源/角色/连接引用 | `space` 的组合关系 | 被引用对象归原领域；关联不搬文件、不发权限 |
| 职责范围关联 / 会话当前背景 | `AI/roles` / `conversations` 分别维护 | Context 中的显示引用不与这两种关系双写 |
| 业务对象与专业关系 | 对应领域；专业对象/关系由模式规则维护 | 无通用“所有边”的业务总管；正式专业数据模型仍未定 |
| 工作流定义、Task、工作轮次、调度占用与运行进展 | `workflows`，内部由 runtime 处理调度事实 | 不与具体连接器的操作状态双写；关图不取消 |
| 单次能力操作、派发尝试、观察结果与回执 | `connections` 的宿主调用责任 | 具体适配器报告；工作流/对话保留关联，不自行改写操作事实 |
| 角色配置、消息与逻辑生成 | `AI` / `conversations` | Provider 调用由 API 适配及连接边界负责，消息不充当操作账本 |
| 产物引用、Review/Verification/Acceptance | `workflows`，关联来源、版本与环境 | 真实文件/提交/远端资源仍以来源系统为据；AI 自报不替代核验 |
| 权限策略、授权决定与撤销 | `permissions` | 操作回执关联当时判定依据，不复制可修改的权限账本 |
| 视图出现/映射、布局与进度投影 | `views` 的视图配置责任；状态从领域派生 | 映射不创建执行依赖，不把缓存写回任务真相 |
| 外部 Session/Agent 循环/实际副作用 | 外部运行时/资源系统 | WEX 保存定位与已知证据，不声称拥有远端完整状态 |

“单一权威”指业务写入口和判定责任，不强制单一数据库或把所有文件放在公共数据根。跨目录持久化、回执与外部副作用之间的原子性尚未验证。通信连接、外部结果、保存状态、任务状态和验收结论是不同维度，不在本轮合成最终状态枚举。

## 7. 七个场景的架构对冲检查

本节为**静态责任/失败推演**，不是并发、恢复或 Windows 运行验收。检查每例的数据 owner、决策、执行、记录与恢复是否有归属，并说明仍缺的证据。

| 场景 | 数据与决策 | 谁执行 / 谁记录 | 故障后的恢复责任 | 检查结论与证据缺口 |
|---|---|---|---|---|
| S1 多个 Space 引用同一 Context | `space` 拥有本体与多处放置；权限域按实际入口/目标判断 | `space` 修改关系；目标领域提供获准数据；各自记录变更 | `space` 处理失联定位/引用；不因解除 A 的引用删除本体或中止 B 的工作 | 可表达；需实测跨目录重定位、重复导入身份、并发删除；不能继承旧单位置限制 |
| S2 多个 Agent 跨项目并发 | 角色职责归 AI，Task/分配/占用归 workflows；runtime 决定协调，permissions 判权 | 外部 Agent/本地适配器执行；连接宿主记操作，workflows 记工作轮次与证据 | runtime 识别共享资源冲突、暂停相关工作并核验；具体执行方处理进程状态 | 责任可表达，未证明并发安全；同一磁盘路径/Git 元数据/外部会话可跨 Context 冲突，外部自发操作不受 WEX 占用保证 |
| S3 外部已改文件后断连 | 文件事实在实际资源；WEX 只知部分操作；断连不推出失败/回滚 | DSH 执行；连接边界记断连/未知和原尝试；workflows 不直接宣布完成 | runtime 暂停冲突重派，经获准连接器查资源版本/产物与可用外部线索；证据不足维持未知，交有权主体处理 | headless 替身断连测试仅覆盖分类；真实文件改动后的恢复/归因未验，禁止盲重试 |
| S4 一张任务图进度映射多张非执行图 | Task 进度归 workflows；业务关系归原领域；呈现映射/投影归 views | 领域更新事实，views 按获准来源投影；不执行映射边 | views 重建落后投影，来源失联标注不可用；领域处理真正业务冲突 | 可表达；图可分别显示执行完/待验证/未验收，不要求同状态；传播暂停/恢复与缓存撤权未运行验证 |
| S5 不同专业模板有同名节点 | 专业规则维护语义，views 只显示；workflows 仅解释明确执行工作流 | 对应规则/执行方处理，记录归所属对象/操作域；不按标题分派 | 模式维护方诊断缺少/不兼容规则，阻止误执行；不静默套用另一专业机制 | 可表达；类型身份/规则版本/更新方式未定；四个 React Flow 节点组件不能证明正式专业节点兼容 |
| S6 DSH 插件还依赖额外服务 | DSH 宿主维护依赖就绪；按实际需要/授权选择补最小服务、外部 DSH 或不支持 | 独立宿主尝试加载并记录诊断；仅就绪能力可经连接边界提供；Task 不由 Loader 改 | 宿主恢复已验证依赖再装载；runtime 处理受影响任务阻塞，不停整个 WEX | 基础依赖激活/卸载/失败有真实实验；DSH 全服务生态未验，Cordis 能加载不等于业务插件能运行 |
| S7 插件未获权请求 WEX 内部资料 | 目标领域拥有资料，permissions 决定授权；插件自报身份/Context 不可信 | 宿主连接边界拒绝回调、不取目标内容并记必要拒绝事实；目标领域保留检查 | 宿主停止失效服务入口、权限域处理撤销，受影响工作由 runtime 报告；不可通过重注册换身份 | 替身已验证拒绝任务读取；跨进程身份、重放/撤权与 OS 隔离未验。若插件可绕过宿主直接读磁盘，接口拒绝不构成系统隔离证明 |

恢复不是默认重新派发；必须区分“事实不足”和“确认没有执行”。未知副作用下可推进无冲突工作，但不能为追求进度释放尚无法判清的冲突资源。普通聊天/单次调用发起的 WEX 受控副作用也须检查该占用，不因没有 Task 而绕过；协调能力由宿主按需装配，不强迫创建工作流实例。当前不选择具体占用、重放或调度算法。
