# WEXPC 按功能聚合的目录与模块设计 V0.1

- 日期：2026-10-28（北京时间）
- 状态：候选设计／待继续细化。用户授权将本轮讨论整理至 WEXPC1；不代表以下路径、接口、crate 划分或迁移方案已冻结。
- 核心原则：**修改局部性。目录和接口应让普通功能修改留在具体模块内，避免维护一个页面或协议需要巡回修改全仓。**
- 产品实现仓：WEXPC。本仓仅研究与设计；本次不修改产品代码、不搬主仓目录、不改变 0.1.1 范围。
- 静态阅读基线：WEXPC main `faf11f31d44e4fc4788e766074b8db6b83ab4a1b`。未运行测试、真实服务或 Windows 验收。

## 1. 已对齐的目标与候选内容

用户已明确：目录与具体代码都需要调整；按完整功能聚合；UI 页面或连接模块的普通修改尽量集中；模块目录放说明和施工规则，帮助 AI 局部维护。当前只有手机，不把人工生成、审核和转交任务卡作为施工前置。

本稿提出的一级目录名、内部文件名、注册方式、存储与构建安排均为候选。下一轮继续细化后，才能形成主仓施工依据。

“一个页面一个文件”本身不是错误。页面展示、按钮、点击处理、局部状态、数据读取与命令提交可以在同一文件。真正的问题是职责越界、实现无限膨胀，以及局部修改不断牵动中央文件。

目标是一个局部功能修改主要发生在一个模块，简单修改通常只改一个实现文件；不是承诺所有修改（包括测试、契约和数据迁移）永远只动一个文件。

## 2. 顶层设计依据

正式产品范围以 [WEXPC 产品基线](https://github.com/owla19s-ux/wexpc/blob/faf11f31d44e4fc4788e766074b8db6b83ab4a1b/docs/PC-PRODUCT-AND-TECH-BASELINE.md) 为准，重点为 §0～§0.3.1、§4.2～§4.3。

1. 上下文体系：Space → 可选 Group → Context；Context 是可自由组合信息、工作和交互关系的环境，不等于软件 Project，不要求所有资源归它所有。
2. 角色体系：Role / Duty / Agent 独立存在；职责关系依工作范围建立，不强制属于某项目或 Space，不从岗位或组织位置推导授权。
3. 数据与策略积累体系：长期研究方向，当前不为它建立空实现或冻结存储、记忆与策略接口。
4. 普通 Conversation 独立可用，不以项目、任务、模板或施工 Agent 为前提。
5. 软件开发是可选模板／工作模式；可提供需求与功能结构、资源映射、交互及流程组合，但不复制通用连接、权限、Dispatcher 和权威任务状态。
6. 连接、权限、执行、Dispatcher、回执和持久化为共享机制；可发现、已选择、可执行、已执行是不同事实。
7. 模板中的图形位置、视图连线和选中态不能成为权威领域状态或授权。
8. 当前研究插件式边界和装配，不把完整动态插件平台、插件市场或外部生态兼容变成前置。

配套依据：
- [架构决策与草案](https://github.com/owla19s-ux/wexpc/blob/faf11f31d44e4fc4788e766074b8db6b83ab4a1b/DECISIONS.md)
- [轻量宿主架构细化](https://github.com/owla19s-ux/wexpc/blob/faf11f31d44e4fc4788e766074b8db6b83ab4a1b/docs/architecture/WEXPC-LIGHTWEIGHT-HOST-ARCHITECTURE-V0.1.md)

上述文件自身的“已确认／草案／历史快照”状态保持有效，不把其中全部候选接口视为正式决定。

## 3. 组织方式与取舍

| 方式 | 取舍 | 本轮处理 |
|---|---|---|
| 全仓按 domain/application/infrastructure 等技术层组织 | 同一功能容易分散，修改要跨多个层级寻找落点 | 不作为目标主轴 |
| 按完整功能聚合，内部按实际复杂度拆分 | 局部维护清晰；需要明确跨模块接口和状态归属 | 本轮采用的设计方向 |
| 全部独立成动态插件、独立包或进程 | 增加运行时、兼容与生命周期工程 | 当前不作为前置 |

目录分类不等于运行时插件分类。目录不要求一一对应 crate、进程、数据库；不得先建全套空骨架。

## 4. 候选顶层职责布局

| 目录 | 责任 |
|---|---|
| `apps/desktop/` | 启动、窗口、生命周期、装配和薄 IPC 桥接 |
| `ui/` | 页面、交互模块、导航壳及复用控件 |
| `workspace/` | Space、Group、Context、组织位置及引用关系 |
| `agents/` | 角色配置、Agent 身份、职责绑定、原生工作循环 |
| `conversations/` | 原生会话、消息、生成状态、引用及续接 |
| `connections/` | 连接实例管理、能力发现及具体接入实现 |
| `work/` | 项目、任务、分工、审查与验证等通用工作事实 |
| `execution/` | 共用执行准入、操作生命周期、结果和回执结算 |
| `dispatcher/` | 队列、派发、依赖、占用、等待及恢复 |
| `permissions/` | 授权、策略、审批、撤销及相关持久化 |
| `templates/` | 可选工作模式的组合定义、专属交互及流程 |
| `platform/` | 凭证库、数据库基础设施和 OS 适配 |
| `tools/` | 架构检查与开发工具 |
| `docs/` | 跨模块架构、权威索引及决策 |

这是目标职责地图，不是当前仓库事实，也不是一次性迁移顺序。`work/` 等分类不能成为新的杂物目录；内部具体维护单元仍需逐项确定。

## 5. UI：按页面聚合

| 候选位置 | 内容 |
|---|---|
| `ui/space/page.tsx` | Space 页展示、按钮、局部交互、数据读取与命令提交 |
| `ui/conversation/page.tsx` | 普通对话页及其交互 |
| `ui/agents/page.tsx` | 独立角色／Agent 管理入口 |
| `ui/connections/page.tsx` | 连接列表、选择及管理入口 |
| `ui/settings/page.tsx` | 通用设置 |
| `ui/shell/` | 导航、页面挂载、窗口布局 |
| `ui/components/` | 确有多个消费者的基础控件 |

- 不强制每页拆 view/controller/hooks/service。
- 简单页面保留一个主文件；只有独立职责或真实复杂度出现时，才在本目录拆消息列表、输入区等。
- UI 可管理草稿、选择、加载与刷新协调；权威业务状态、持久化规则、权限裁决和实际工具执行归底层。
- 页面调用稳定接口；普通交互修改不要求同步修改 Host、领域规则和存储。
- 全局 App 不继续吸收每个页面的发送、恢复、草稿和表单逻辑；共享快照一致性机制保留一个明确维护位置。
- 连接专属设置面板由连接模块贡献；模板专属面板由模板贡献。页面宿主挂载，不复制实现。

## 6. 连接系统：按来源聚合，按协议扩展

| 候选位置 | 内容 |
|---|---|
| `connections/catalog/` | 连接实例、配置修订、启停、适配器登记与能力发现 |
| `connections/api/` | 模型调用标准、API 配置与专属面板 |
| `connections/api/protocols/` | 各模型协议适配实现 |
| `connections/github/` | GitHub 配置、声明、操作实现及专属面板 |
| `connections/local-files/` | 本地文件读写、配置及资源适用检查 |
| `connections/terminal/` | 进程／终端接入 |
| `connections/git/` | 本地 Git 能力 |

一个协议实现可完整包含该协议请求编码、响应解码和错误转换，复杂后才拆本地子文件。新厂商若兼容已有协议，可能只需要配置；不能机械地一厂商复制一份协议。

通用聊天、工具回合通过适配接口调用，不直接认识具体厂商协议。协议模块仅返回模型输出及工具意图，不执行工具。

普通新增适配器目标：新增本模块声明、实现和测试，经统一机制装配；不再修改中央厂商枚举、聊天分支和工具回合解析器。构建期收集、显式注册或其他机制尚待验证；不承诺当前已能“放文件自动识别”，也不承诺无需重建的动态加载。

专属 TS 面板与 Rust 实现可在同一功能目录内分别组织，由各自构建入口消费。这是维护布局建议，Cargo、TypeScript/Vite、Tauri 的具体接线和依赖限制尚未验证。

## 7. 工作空间、角色、会话和工作事实

`workspace/` 内可先使用 `space.rs`、`group.rs`、`context.rs`、`relations.rs` 等功能文件及就近测试。不把每个功能重新分散到全仓技术层目录。具体持久化文件随本模块归属；数据库连接、事务基础设施才属于公共平台。

- Context 组织背景及关联，不拥有所引用连接、Agent 或外部文件。
- 角色／Agent 的身份、配置和职责由 `agents/` 管理；会话不等于 Agent。
- `conversations/` 管理会话事实；原生 Agent 循环和会话生成协调如何衔接，下一轮细化唯一 owner。
- `work/` 管理通用项目与任务事实；软件开发不是它唯一消费者。
- Dispatcher 记录投递过程与尝试，不复制 Task 正式状态；Task 变更通过其权威入口。
- 外部 Agent Session 由外部管理，WEX 只保存自己的定位、交接和证据，不默认为原生会话。

## 8. 软件开发模板：专属内容一起维护

| `templates/software-development/` 内 | 内容 |
|---|---|
| `template.*` | 身份、默认组合、能力需求与视图登记 |
| `structure.*` | 需求／功能结构定义及实例化映射 |
| `panel.tsx` | 软件开发工作面板 |
| `views/` | 必要时拆分的功能树、资源映射等专属交互 |
| `workflow.*` | 施工、审查、验证的流程定义 |
| `tests/` | 模板及组合行为验证 |
| `MODULE.md` | 职责、具体落点、接口和修改规则 |

星号表示格式／语言待定，不是要求同名多份实现。

模板声明组合并通过通用服务实例化，不能拥有第二套任务存储、权限或连接实现。模板专属结构允许有代码与数据定义，但底层对象身份和权威写入口必须明确；专属数据如何挂接通用对象仍需细化。

模板应用后的真实工作数据属于实例。模板更新不得静默覆盖用户任务、资料或关系。完整继承、市场和自动迁移不在本稿启动。

工作流定义属于具体模式；通用等待、依赖、派发与恢复使用现有机制。不另造与 Dispatcher 重叠的工作流引擎。通用流程解释职责与 Dispatcher 的具体接口待定。

## 9. 权限、执行与平台

`permissions/` 集中维护授权、策略、审批、撤销和自己的记录逻辑。其他模块提供主体、动作、资源、范围和所需权限，不各自维护一套政策。

执行入口组织判定与操作登记；最终执行边界保留 OS、资源版本和适用权限复检。检查发生在不同位置，不意味着重复政策真相。

凭证值由平台凭证服务管理，不能进入普通连接配置。资源引用、模板启用、界面勾选都不自动授权。

权限规则修改应主要落在权限模块；新增连接的操作声明主要落在该连接模块。具体接口必须支持这种局部性，不能只是把文件搬家。

## 11. 模块说明与 AI 施工

每个实际维护单元就近放 `MODULE.md`，最少说明：

1. 职责与非职责。
2. 具体功能 → 文件位置，包括常见修改示例。
3. 对外接口、允许依赖、禁止穿透的内部实现。
4. 数据／状态 owner；UI 草稿与权威状态分别说明。
5. 新增同类功能如何接入。
6. 验证命令、已知限制、当前未实现项。
7. 哪些变化需要协调契约或数据迁移。

不复制大段全局口号，不强制所有模块套连接器模板。无需用户每次手工转交施工任务卡；AI 从仓库入口找到模块规则，定位后执行与验证。

根入口后续需要明确现行文档和模块规则的读取方式；`MODULE.md` 不会因文件名存在就保证所有 AI 自动读取。

## 12. 局部性验收与后续细化

| 修改场景 | 预期主要落点 |
|---|---|
| Space 页按钮、布局、反馈 | `ui/space/` |
| 新模型协议 | `connections/api/protocols/` |
| GitHub 文件读取行为 | `connections/github/` |
| 软件开发模板面板与流程 | `templates/software-development/` |
| 通用撤权规则 | `permissions/` |

测试和必要接口迁移不计作“禁止多文件”。评判的是是否因错误耦合不得不修改无关模块；不能通过删除测试或把所有代码塞进一个文件达到指标。

下一轮优先细化：
- 各模块唯一数据 owner、入口及允许依赖；特别是 Agent 循环／会话、任务／Dispatcher／执行、模板流程之间。
- Rust crate、前端包与目录的映射；是否保留部分现有物理路径。
- 插件声明、注册和 UI 挂载标准；旧连接如何选择适配器。
- 模板专属数据、用户实例数据、视图状态及更新规则。
- 真实调用链的逐文件归位、迁移顺序及兼容策略。
- 最小结构检查，防止跨模块内部引用及中央分支重新膨胀。

在这些问题收敛前，本稿用于讨论，不作为主仓搬迁施工令。
