# WEX 交互语义与 UI 映射边界

- 日期：2026-11-01
- 关联主表：[WEX 产品基础功能总表](PRODUCT-FUNCTION-CATALOG-2026-11-01.md)
- 状态：交互语义目录首轮整理；不冻结页面、视觉、组件、快捷键或 UI 技术实现。
- 原则：先完成基础功能和可调用契约，再根据这些契约设计 UI；最终产品验收必须包含真实用户操作链路。

## 1. 为什么必须分开

WEX 需要同时维护三种不同的规格。它们有关联，但不能合并成一张“用户功能按钮表”。

| 规格 | 回答的问题 | 例子 | 当前处理 |
|---|---|---|---|
| F：基础功能 | 系统能够做什么，业务结果由谁维护 | 创建 Context、调用模型、执行文件修改、恢复 Task | 当前优先细化和独立验收 |
| I：交互语义 | 用户或其他参与者提出什么业务意图，系统如何解释 | 创建、关联、授权、派发、停止、验收 | 先定义语义和结果，不设计具体控件 |
| U：UI 呈现与操作 | 用户通过什么界面、控件和输入方式发起 I 行为 | 页面、按钮、菜单、拖拽、快捷键、语音、浮动面板 | 后置设计与接线，最终进行真实用户验收 |

### 1.1 基础功能不等于 UI 操作

“创建 Context”是一项基础业务能力。它必须能够通过稳定接口被 UI、API、Agent 或工作流调用。

“点击新建按钮”是 UI 操作。按钮本身不拥有 Context 数据，也不负责生成 Context 的权威身份。

“创建成功”必须由 Space owner 的真实提交结果证明。UI 不能因为按钮被点击、动画结束或本地状态改变，就显示正式创建成功。

同样：

- 勾选消息段落 ≠ 采纳观点。
- 采纳观点 ≠ 修改正式需求。
- 修改正式需求 ≠ 创建 Task。
- 创建 Task ≠ 授权工具操作。
- 授权工具操作 ≠ 已派发。
- 已派发 ≠ 外部已完成。
- 外部已完成 ≠ Verification 通过。
- Verification 通过 ≠ 最终 Acceptance。

### 1.2 交互语义也不等于 UI 控件

一个业务动作可以由多种入口发起：

- 用户通过 UI 发起；
- 用户在对话中用自然语言提出；
- Agent 通过受控能力接口提出；
- 工作流按规则触发；
- 外部服务通过可信回调触发。

它们必须进入同一业务 owner 和权限边界，不允许 UI、Agent、API 各自实现一套业务逻辑。

### 1.3 当前优先级

当前施工顺序：

1. 完成 F01–F15 基础业务能力定义。
2. 完成模块公开能力和 I 级交互语义。
3. 验证模块独立能力和跨模块组合。
4. 再设计 U 级 UI 页面、控件、导航、鼠标/键盘/语音操作。
5. 将 F、I、U 映射到真实桌面流程，进行最终用户验收。

模块测试不是最终产品验收，但没有模块独立测试，也不能把 UI 接线当作第一次业务验证。

## 2. F / I / U 三类编号规则

- F01-xxx：基础功能编号，定义产品能力。
- I01-xxx：交互语义编号，定义一个可解释的业务意图和操作结果。
- U01-xxx：未来 UI 映射编号，待 UI 设计阶段建立。

同一 I 行为可以调用多个 F 能力；同一 F 能力可以被多个 I 行为或非 UI 入口调用；一个 U 页面也可以组合多个 F/I。

不得用 UI 页面编号替代基础功能编号，也不得让某个页面成为跨模块业务状态 owner。

## 3. 交互语义目录 I01–I16

本目录不是按钮列表。每项只定义业务意图、必要信息、调用边界和结果区分。

| 编号 | 交互语义 | 业务含义 | 主要 F 域 | 权威处理方 |
|---|---|---|---|---|
| I01 | 创建与初始化 | 请求建立新对象或新配置 | F01/F02/F03/F07/F08 | 对象所属 owner |
| I02 | 查看与检查 | 查询对象、状态、来源和历史 | 全部 | 对象所属 owner |
| I03 | 编辑与修订 | 对已有对象提交带预期版本的修改 | 全部 | 对象所属 owner |
| I04 | 选择与引用 | 将对象/资料/消息作为当前工作输入 | F01/F03/F10/F11 | 引用方保存引用；来源 owner 维护本体 |
| I05 | 关联与解除 | 建立或解除对象之间的关系 | F01/F02/F07/F11 | 关系所属 owner |
| I06 | 配置与组合 | 选择模型、Agent、连接、工具、模板和资源组合 | F01/F02/F04/F05/F07 | 配置所属 owner |
| I07 | 启用与停用 | 启用/停用模块、连接、能力或扩展 | F05/F12/F14 | 对应 owner；app 负责装配 |
| I08 | 提议与预览 | AI 或用户提出变更草案，不立即修改正式事实 | F03/F07/F11 | 提议来源可追溯；正式 owner 未改变 |
| I09 | 采纳与拒绝 | 对建议、序列项、审查意见或候选变更作出决定 | F03/F07/F08/F13 | 对应对象 owner |
| I10 | 授权与撤权 | 对主体、入口、资源、动作和范围作出许可决定 | F09 | permissions |
| I11 | 派发与执行 | 请求开始 Task、Workflow 或单次 Operation | F05/F07/F08 | workflows / connections |
| I12 | 暂停、继续与停止 | 对排队、Task、Execution 或外部 Operation 发起控制 | F08/F05 | workflows / connections |
| I13 | 观察与恢复 | 查询原工作状态、核对外部事实并安全接续 | F03/F05/F08/F10/F15 | 各事实 owner |
| I14 | 审查、验证与验收 | 对具体版本和证据进行 Review、Verification、Acceptance | F13 | workflows；权限由 permissions |
| I15 | 导入、导出与恢复数据 | 在明确范围内迁移、备份、导入和恢复 | F10/F14/F15 | 数据 owner + app/shared 技术接线 |
| I16 | 搜索、通知与定位 | 查询可见对象，通知待处理事项并导航到来源 | F01/F03/F08/F11/F15 | 各领域提供数据；UI 聚合呈现 |

### 3.1 I01–I07：对象管理类行为

**I01 创建与初始化**

必要信息：目标类型、创建范围、初始配置、来源或模板（可选）、调用主体和入口。

结果区分：创建成功、已存在/重复意图、拒绝、校验失败、提交未知。

约束：创建 Space 不自动创建 Context；创建 Context 不自动创建 Project/Task/Agent；从模板创建不自动启用所有连接和权限。

**I02 查看与检查**

必要信息：对象身份、查询范围、当前主体和入口。

结果区分：有权返回、无权、目标不存在、来源失联、数据不可用、结果过期。

约束：缓存和搜索命中不能绕过读取权限；历史授权不等于当前可见。

**I03 编辑与修订**

必要信息：目标身份、预期修订、规范化变更、操作意图。

结果区分：提交成功、版本冲突、业务拒绝、确定未提交、提交未知。

约束：不得最后写入覆盖；未知提交必须按原意图回读，不得直接换新意图重写。

**I04 选择与引用**

必要信息：对象稳定身份、来源版本、引用目的和可见范围。

结果区分：引用成功、目标失效、无权引用、来源版本变化。

约束：引用不复制权威数据，不自动创建关联，不授权后续读取或外发。

**I05 关联与解除**

必要信息：关系类型、双方对象身份、作用范围、预期修订。

结果区分：建立成功、关系冲突、解除成功、解除失败、结果未知。

约束：层级、一般关联、资源引用、执行依赖和权限关系不可混用；解除引用不删除目标。

**I06 配置与组合**

必要信息：配置 owner、配置修订、引用能力、覆盖规则和冲突处理。

结果区分：配置已保存、部分能力不可用、配置冲突、保存未知。

约束：选择能力不等于授权；模板配置不等于运行实例；配置变化不静默重定向在途操作。

**I07 启用与停用**

必要信息：目标模块/连接/插件/能力、主体、适用范围。

结果区分：已启用、已停用、依赖缺失、停用未完成、在途操作仍未知。

约束：停用通常阻止新调用，不代表已取消外部运行或回滚副作用。

### 3.2 I08–I10：提案与决策类行为

**I08 提议与预览**

提案必须保留提出者、来源、目标对象、预期修订和差异。预览不写入正式数据、不申请权限、不调用外部副作用。

**I09 采纳与拒绝**

采纳对象可以是消息观点、结构建议、Task 草案、审查意见或某个字段变更。每种采纳都必须指向明确目标和后续业务动作。

不得用一个含糊“确认”语义同时完成采纳观点、保存数据、批准权限、派发任务和最终验收。

**I10 授权与撤权**

授权请求必须明确主体、真实入口、目标资源、动作和范围。批准绑定具体请求，不批准任意自然语言内容。

撤权影响后续受控读取和派发；不自动停止外部 Agent、不删除已发送数据、不回滚已发生操作。

### 3.3 I11–I14：执行与验证类行为

**I11 派发与执行**

必须区分：计划生成、队列登记、权限允许、资源协调、Operation attempt 保存、真实派发、外部受理和结果观察。

任何一个阶段失败，都不能跳过前置步骤把状态直接改成执行成功。

**I12 暂停、继续与停止**

对象必须明确是 Task、Workflow、Execution、Operation 还是外部 Session。

取消排队项、请求停止外部执行、停止等待、确认外部停止和补偿副作用是不同动作。

**I13 观察与恢复**

必须查询原 Task/Operation/Session 和真实资源状态。恢复不等于新建任务重发；外部 not found、timeout 或进程退出都不自动证明没有发生副作用。

**I14 审查、验证与验收**

Review、Verification 和 Acceptance 分别记录主体、目标版本、证据和规则。模型自述通过不能替代实际工具证据；验证通过不能自动代表用户接受，除非适用规则明确授权自动 Acceptance。

### 3.4 I15–I16：数据与信息导航类行为

**I15 导入、导出与恢复**

必须明确数据类型、来源、目标、身份冲突、凭证排除、权限和失败后的部分完成状态。导入旧数据不能自动恢复有效凭证或授权。

**I16 搜索、通知与定位**

搜索和通知只提供获准结果的索引与入口，不拥有业务事实。点击旧通知或搜索结果时重新读取 owner 当前状态并判权。通知丢失不能丢失 Task/Operation 本身。

## 4. 用户输入与交互载体

以下是未来 UI/输入方式可能承载的交互形式，不代表当前已决定页面或组件。

| 输入/载体 | 可表达的交互 | 必须保留的语义 |
|---|---|---|
| 鼠标点击 | 选择、打开、提交、批准、取消等 | 点击目标身份和动作明确；危险操作不误触 |
| 拖放 | 添加资源、调整布局、关联对象、导入文件 | 视觉拖线不自动变业务关系；路径需校验 |
| 键盘/快捷键 | 搜索、导航、选择、快捷操作 | 焦点范围、快捷键冲突和可撤销性明确 |
| 语音 | 选择对象、指向序列项、提出修改或执行请求 | 当前选中对象作为上下文但不扩大权限；歧义需澄清 |
| 自然语言对话 | 提议、查询、修改草案、创建 Task、请求执行 | 普通描述不自动变成正式写入或工具授权 |
| API/自动化 | 查询、创建、更新、触发工作流 | 可信主体、入口、幂等和权限与 UI 一致 |
| 外部回调 | 回传执行状态、产物和事件 | 来源认证、范围、重放防护和事实归属明确 |

## 6. 最终 UI 验收要求

基础模块独立验收和 UI 最终验收不是同一件事。

### 6.1 基础模块阶段

必须证明：

- 业务逻辑、数据归属和状态生命周期正确。
- 公开能力可以被独立调用。
- 权限、并发、异常、取消和恢复语义正确。
- 正常和负向路径可执行测试。
- 不依赖某个具体 UI 页面才能成立。

### 6.2 模块组合阶段

必须证明：

- 公开契约之间真实接通。
- 唯一权威状态没有重复写入。
- 事件、Operation、Task、Evidence 和 Verification 正确关联。
- 多 Agent、多 Context、多入口和资源冲突可处理。
- 外部结果未知时不会盲目重派。

### 6.3 UI 最终产品阶段

必须从真实用户角度验证：

- 用户能够发现并理解可用能力。
- 用户能创建、配置、选择和组合工作环境。
- 普通对话不需要先建立项目或 Task。
- 用户能从对话或对象入口提出变更，并清楚区分建议、采纳、授权和执行。
- 用户能看到实际运行状态、失败原因、结果未知和验证证据。
- 关闭页面、切换 Context、重启程序后能恢复正确事实。
- 页面缓存、通知和搜索结果不会绕过权限。
- 鼠标、键盘、语音、拖放等具体交互不会改变底层业务语义。
- 完成一条真实端到端工作流程，而不是只证明页面能打开、按钮能点击。
- 覆盖高 DPI、多显示器、键盘完整操作、可访问性、长文本、中文路径/英文系统和本地化错误信息。
- 覆盖鼠标、键盘、语音、拖放和系统通知的交互一致性；具体支持范围以实际平台验收为准。

**最终 UI 验收是产品可用性的验收，不是第一次验证底层业务逻辑。**
