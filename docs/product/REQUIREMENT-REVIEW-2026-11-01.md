# WEX 产品需求对冲与遗漏审查记录

- 日期：2026-11-01
- 依据：[基础功能总表](PRODUCT-FUNCTION-CATALOG-2026-11-01.md)、[交互/UI 边界表](INTERACTION-AND-UI-BOUNDARY-2026-11-01.md)、当前 main 模块 README/CONTRACT、G1–G7、H01–H30 和旧 WEXPC 产品基线。
- 状态：首轮跨域审查记录；不是所有候选需求的批准书，不改变当前版本范围。
- 目标：确认功能域归属、找出遗漏和重复、明确未决风险，并建立下一轮对冲入口。

## 1. 审查结论

### 1.1 总体结论

F01–F15 可以继续作为产品功能域主骨架，但必须把基础功能、交互语义和 UI 呈现分开管理。

当前最明显的问题不是“缺少一个大模块”，而是以下横向基础机制在多个模块中出现，却缺少清晰的权威归属和端到端规则：

1. 对象身份、资源身份与关系类型。
2. 配置归属、修订和在途配置快照。
3. 事件、通知、命令与跨模块状态同步。
4. 操作未知、恢复、资源占用和并发协调。
5. 数据导入导出、备份恢复和数据根接回。
6. 日志、审计、回执、产物和验证证据的边界。
7. 本机安装、单实例、崩溃恢复、Windows 权限与系统集成。
8. Agent 记忆、公共策略和知识来源可信度。

这些能力应先作为跨模块基础契约明确，不急着新增顶层模块或目录。

### 1.2 不应发生的产品缩减

以下需求不能因为当前工程模块较少、UI 尚未施工或首版尚未规划，就从完整产品需求中删除：

- Context 可以独立存在，也可以跨项目/Context 建立关系。
- 普通对话不以 Project、Task、Agent 或模板为前置。
- Agent、角色、职责、模型、会话、连接和授权分离。
- 用户授权范围内支持多 Agent 真实并发施工，不是并行聊天演示。
- 本地文件、终端、Git、开发工具链和 Android SDK/模拟器属于本地开发能力范围。
- 软件开发是第一个专业模板，不是所有 Context 的固定结构。
- Task、Operation、Execution、Receipt、Artifact、Evidence、Review、Verification、Acceptance 分开。
- 外部 Agent 继续作为独立客户端，由连接器交接；WEX 不复制其内部 Agent Loop。
- 自由画布、多视图、架构树/功能树和浮动入口保留完整产品方向，但 UI 深度和版本归属另行决定。
- 项目工作记录、基准、快照、任务、回执、验证证据和 Git/文件真实状态必须可持续恢复。
- 用户可选数据目录与程序安装目录分离；重装后可接回普通资料，但凭证和有效授权不得自动恢复。

依据：旧 WEXPC 正式产品基线的 PC 迁移补充及当前 WEXPCeasy 模块契约。该继承是产品需求回收，不是旧实现/技术路线迁移。

### 2.1 新发现但不建议独立成域的横向机制

| 横向机制 | 建议归属 | 需要明确的契约 | 不应建立的重复系统 |
|---|---|---|---|
| 对象身份/关系 | 各领域 owner | 稳定身份、关系类型、修订、删除影响 | 全局万能 Object DB |
| 资源定位/别名 | 资源实际 owner + connections/local | 路径、真实资源身份、别名、失联和重定位 | 全局资源内容副本 |
| 配置 | 各模块 owner | 默认值、覆盖、版本、迁移、生效和在途快照 | shared 业务配置总管 |
| 事件/命令 | 事件所属 owner；宿主装配传递 | 来源、顺序、去重、失败、补偿和回读 | 第二套全局业务状态库 |
| 通知 | 领域 owner 提供事实；UI/app 呈现 | 过期、撤权、点击重查、送达失败 | 独立通知业务真相 |
| 搜索 | 各 owner 查询；UI 聚合 | 可见性、索引新鲜度、失联、跨 Context | 绕权的全局内容查询服务 |
| 网络/代理 | app 通用偏好；连接器具体适配 | Provider 级代理、证书、离线和重连 | 所有连接器共享一个不可配置代理策略 |
| 日志/诊断 | shared 技术支持；各 owner 正式账本 | 脱敏、保留、轮转、导出和失败降级 | 用日志替代 Operation/审计/验收 |
| 定时/自动唤醒 | app + workflows/runtime，待政策 | 触发条件、授权、成本、暂停和恢复 | 未经决定的后台常驻调度器 |

| F14 / F10 | 安装器决定所有数据的业务迁移规则 | app 负责协调；各 owner 验证自身数据迁移 |
| F15 / F09 | 普通日志承担权限审计 | permissions 保存审计事实；日志仅提供技术观察 |

### 3.1 必须保留的核心对象分离

- Capability ≠ Connection ≠ Service ≠ Resource。
- Object ≠ Resource ≠ Relation。
- Space ≠ Context ≠ Project。
- Agent Definition ≠ Role ≠ Actor ≠ Agent Instance ≠ Session。
- Provider ≠ Account ≠ Credential ≠ Model。
- Conversation ≠ Task。
- Workflow Definition ≠ Workflow Run ≠ Task。
- Task ≠ Execution ≠ Operation。
- Operation Receipt ≠ Artifact ≠ Evidence。
- Review ≠ Verification ≠ Acceptance。
- Module ≠ Plugin ≠ Connector ≠ Template。
- Domain State ≠ View Projection ≠ UI Local State。

任何模块契约出现上述概念合并，都应回到本节对冲。

## 4. 基础能力验收与 UI 验收的分界

### 4.1 基础功能验收

每个模块独立证明：

- 输入输出和业务规则正确。
- 数据由正确 owner 持有。
- 生命周期和修订正确。
- 依赖通过公开能力接入。
- 权限和可信入口正确。
- 失败、拒绝、超时、取消、未知状态正确。
- 并发和恢复不破坏权威事实。
- 测试能在不依赖最终 UI 的条件下执行。

基础验收可以使用测试调用器、CLI、替身或真实适配器，但必须标明证据等级，不能把替身测试当成真实外部服务验收。

### 4.2 模块组合验收

通过真实提供方和消费者组合，检查：

- 跨域依赖方向。
- 唯一权威状态。
- 事件和回执传递。
- 授权执行前复核。
- 资源冲突和并发。
- 失败恢复与未知副作用。
- 多 Context、多 Agent、多入口和外部系统交接。

### 4.3 UI 最终验收

UI 阶段才验收：

- 页面、导航、控件和输入方式是否合理。
- 用户能否发现、理解、配置和组合基础能力。
- 用户的每种操作是否准确映射到 I 语义。
- 状态展示是否与权威 owner 一致。
- 复杂任务能否由真实用户从头到尾完成。
- 鼠标、键盘、拖放、语音、通知和多窗口是否可靠。
- 错误、冲突、未知、审批和恢复是否对用户清晰可处理。

UI 最终验收不是要求底层第一次通过业务验证；它是整套产品面向真实用户的最终可用性验收。

以下是覆盖缺口，不自动批准新增产品功能，也不直接建立新正式 H 编号。只有与现有 H01–H30 存在独有失效机理时，才补充专项样本。

### 6.1 当前不新增独立产品域的理由

- 搜索、通知和帮助更适合作为各领域数据的聚合与 UI 导航能力，暂不新增顶层业务 owner。
- 配置、事件、日志、诊断、凭证和存储属于横向技术支持，不应集中管理所有业务含义。
- 资源身份应由真实资源 owner 提供；不新增万能资源管理模块。
- Dispatcher 是确定性调度机制，不是一个模型角色，也不需要为了概念完整而先建立独立 OS 常驻进程。
- 插件市场、账号云服务和跨设备同步是长期扩展，不是个人本地首期必需。

## 8. 需求优先级与完整产品范围边界

本轮不做版本裁剪，但可以为需求完整性建立类型标签：

| 类型 | 含义 | 示例 |
|---|---|---|
| 基础必需 | 产品不具备就无法安全运行或完成核心目标 | 持久化、授权、Operation、Task、错误/未知、恢复、宿主装配 |
| 核心工作能力 | 个人工作和软件开发核心流程需要 | Space/Context、对话、模型、连接器、本地工具、多 Agent、Workflow、Evidence |
| 产品交互能力 | 需要用户可理解、可控制和可观察 | 对话序列、选择/引用、审批、视图、通知、搜索 |
| 桌面保障能力 | 正常安装和长期使用必须考虑 | 安装、单实例、数据根、更新、诊断、网络、资源维护 |
| 长期扩展 | 保留产品方向，不作为首期默认前置 | 多设备同步、账号云服务、插件市场、公共知识库、跨行业模板、角色形象/TTS |

“基础必需”不代表所有能力都由 shared 或 app 实现；它表示产品必须具备，owner 仍按 F01–F15 明确。
