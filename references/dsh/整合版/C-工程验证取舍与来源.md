# C｜工程规则、验证、取舍与来源映射

状态：研究整合／候选建议，不替代 WEX 当前设计文档。

## 1. 工程规则去重（原 04、06、15）
DSH 通过包级 README、接口与限制说明、AGENTS、adding-a-package、依赖/导出/元数据校验及类型检查，把工程知识转成可执行门禁。AI 施工应就近阅读模块职责、允许依赖、状态 owner、常见修改落点和验证命令；**机器可检查的规则不应只靠文档自觉**。施工卡是可选的任务组织方式，不应成为 WEX 用户每次手工转交的前置要求。

## 2. 需求反向压测（原 08、11、15）
检查链路：用户需求→对象身份→模块契约→能力发现→授权→运行时执行→可信回执→恢复→UI。秘书、主 AI、执行 AI 的 Role/Duty/Agent 与模型 Provider、API Key、工具授权必须分离；不能根据角色名称直接授予权限。出现不满足需求的情形时先定位对象/协议/策略/运行时缺口，不以新增中央 if/else 掩盖。

## 3. 建议优先级（不代表 0.1.1 范围变更）
- **先明确契约**：能力/连接身份、模块注册与生命周期、Host/Client、操作/回执 owner、依赖边界。
- **先做最小验证**：未知协议与设置面板运行时加载；停用拒绝新调用；回执 flush 与崩溃恢复；依赖机器检查。
- **随后增强**：配置修订、凭证热轮换、只读投影、Context 摘要、Workflow/子 Agent 能力差异。
- **延后研究**：完整脚本 VM、插件市场、复杂多主体安全体系、任意原生代码无缝 HMR。

## 4. 不照搬清单
1. Cordis Scope 不是安全沙箱，也不能直接表达多 Space/组织的复杂共享关系。
2. 不把全部 WEX 领域数据塞入单个 Session。
3. 不把“配置热更新”当作“原生代码热替换”；HMR 不保证外部副作用回滚。
4. 不因参考 DSH 重造 WEX 已存在的工具回合、预检、checkpoint 和恢复保护。
5. 不机械恢复 WEXPC1 旧资料中的“所有模块禁止直接依赖”规则；以当前功能聚合和公开契约设计为准。
6. 研究资料不等于已实现；需要明确静态阅读、模拟测试、真实服务和 Windows 验收证据。
