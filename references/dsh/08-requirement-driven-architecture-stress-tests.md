# WEX 需求反向压测：角色、API 与执行权限

- 状态：需求驱动的架构审查方法 / 候选约束；不是已冻结的底层设计
- 目的：用真实产品需求检验现有架构是否成立，避免架构自洽但产品无法实现。

## 1. 基本原则

WEX 的架构审查不能只验证模块是否边界清晰、接口是否优雅，还必须验证这些模块组合起来能否实现已确认的用户需求。

每个核心需求都应沿着完整链路反向压测：

**需求 → 对象模型 → 模块接口 → 协议 → 权限边界 → 运行时行为 → 验证条件 → AI 施工卡**

若需求无法通过现有设计自然实现，应定位并修正底层缺口；不得仅靠给业务模块增加临时特例来维持表面兼容。反过来，单个需求也不能自动成为推翻整体架构的理由，必须先确定缺口属于对象模型、接口、协议、策略、运行时还是实现。

## 2. 角色系统对 API 设计的反向约束

WEX 已有的产品方向要求分离以下概念：

- **Provider / API 连接**：服务端点、供应商协议、连接配置。
- **Credential**：可用于连接的密钥或凭证，具有独立的保存和使用边界。
- **Model**：模型标识、参数和能力元数据。
- **Role / Duty**：当前身份与职责，例如秘书、主 AI、施工 AI、审查 AI；角色定义工作职责，不等同于系统权限。
- **Agent / Participant**：实际参与协作的执行主体或实例。
- **Conversation / Task / Workspace**：工作发生的上下文、任务范围和资源边界。
- **Capability / Tool**：主体在当前组合中能够请求的操作能力。
- **Grant / Policy / Approval**：授权来源、适用范围、决策规则与必要的审批。

以上是需要保留的概念区分，不预设它们最终必须各自成为独立模块或数据库表。

## 3. 场景压测：秘书与普通施工 AI

### 场景 A：秘书自主选择模型

用户允许秘书在预算、供应商和隐私策略范围内选择模型。秘书需要能查询可用模型、比较能力，并为特定任务选择模型。

必须验证：
- 角色职责与模型选择策略可以独立配置。
- 模型可用性不意味着当前角色获准使用对应凭证。
- 选择模型不会隐式扩大工具、文件、仓库或执行权限。
- 切换模型后，任务身份、授权范围、操作回执和审计链不丢失。
- 预算、Provider 限制和用户禁用项仍由系统策略强制执行。

### 场景 B：施工 AI 使用受限模型与工具

施工 AI 只获得任务卡指定的资源范围、可用工具与执行方式。

必须验证：
- 子任务不能自行扩大授权范围；超范围请求应明确拒绝或升级。
- Prompt 中的角色描述不能成为授权凭证。
- 模型可见工具清单、实际执行检查与最终安全边界保持一致。
- 即使更换模型或工具适配器，任务范围与强制拒绝规则仍然生效。
- 并行任务不能通过共享会话或连接状态意外继承彼此的权限。

### 场景 C：同一角色更换模型或调用多个模型

同一个角色可以在不同任务中使用不同模型；必要时也可以调用一个模型执行、另一个模型审查。

必须验证：
- Role 不与单个 Model 或 Provider 永久绑定。
- 模型路由属于能力选择，不是角色身份变化。
- 每次模型调用的 Provider、Model、Credential 引用、任务和结果可追踪。
- 调用失败、重试、切换 Provider 时，幂等性和操作状态不被混淆。
- 模型不能因为是“审查模型”或“主模型”就获得额外执行权。

## 4. 权限结构必须同时满足灵活与严格

WEX 需要允许 AI 在已授权范围内自主组合工具与多步工作流，而不是把所有工作流写死；同时，底层真实操作边界必须稳定且可强制。

既有权限分层方向包括：

1. **连接／模块启用**：某类服务是否在当前安装和运行配置中启用。
2. **资源与访问授权**：允许访问哪些项目、目录、仓库、连接和数据，以及读写范围。
3. **主体／会话／执行策略**：当前 Agent、任务或会话能否使用某项能力，遇到哪些操作需要自动放行、询问或拒绝。

角色、岗位、任务和会话可以作为策略判断的输入，但不能直接替代授权。高权限秘书可以在授权范围内连续执行多步操作，无需每一步都向用户询问；这不代表它能绕过全局禁用、资源边界或不可覆盖的强制拒绝。

## 5. DSH 源码可借鉴的具体机制

DSH 的工具执行链提供了一个可研究的实现参考：

- `tools/pre-execute`：可扩展策略流水线，给出允许、拒绝或询问的决策。
- `ctx.tools.guard()`：在可扩展策略之后执行单调拒绝检查；guard 能拒绝或弃权，不能把已被强制规则拒绝的调用重新放行。
- `tools/execute`：包围实际派发过程，适合超时、重试与指标等机制。
- `tools/post-execute`：检查或转换执行结果。
- `tools/result`：观察规范化后的最终结果。

参考：[DSH 工具注册与执行管线](https://github.com/DeepSeek-AI/deepseek-harness/blob/master/packages/core/tools/README.md)、[扩展点设计指南](https://github.com/DeepSeek-AI/deepseek-harness/blob/master/docs/cookbook/extension-cookbook.md)。

可借鉴的是“可扩展策略 + 不可被后续插件推翻的最终约束”的分工，不代表 WEX 必须复制 DSH 的 API、事件名或内部实现。

## 6. 每项需求必须形成的审查记录

每个需求至少记录：

1. **需求事实**：用户已确认的行为；与建议、假设分开。
2. **受影响对象**：涉及的身份、职责、模型、凭证、任务、连接、资源与能力。
3. **模块与接口**：谁拥有状态，谁提供能力，谁负责调用边界。
4. **协议约束**：请求、结果、错误、取消、重试、版本和兼容行为。
5. **权限路径**：策略由谁计算，强制边界在哪里，回执记录什么。
6. **运行时验证**：正常、拒绝、超范围、并发、故障恢复和切换场景。
7. **施工卡输出**：明确依赖、允许修改范围、验收证据与未决问题。

若某项需求无法映射到具体接口和可执行验证条件，应标记为设计缺口，不得直接交给 AI 自由补全。

## 7. 审查边界

- 本文用于检验架构，不是对现有 WEXPC1 模块目录或协议的最终裁决。
- 角色权限示例不得简化为单一的 `role -> permission level` 数字；实际授权还需考虑资源、动作、主体、会话、任务和策略来源。
- 不要求所有能力都固定为预定义工具；允许可扩展的能力组合，但必须经过统一的授权与执行边界。
- 只有当多个真实需求和实现证据共同表明现有抽象不足时，才调整底层结构。
