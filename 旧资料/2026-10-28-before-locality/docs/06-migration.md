# 06 — 迁移方案：从现有仓库到目标结构

> 原则：**不搞大爆炸，不重写已验证的安全实现，不保留两套并行真相。** 迁移是一系列可验证的小步，每步都有退出条件。
>
> **V0.2 修订**：WEXPC 主仓已进入活跃开发（Tauri + React、`wex-api`、`wex-desktop-service`、`contracts`、不可变回执/检查点）。因此迁移**不能从“搭新骨架”开始**，必须从“资产盘点”开始；目录是最后一步，不是第一步。

## 1. 迁移原则

1. **先盘点，再定规则，再动代码。** 不知道现有资产是什么，就无法判断“复用/适配/替换/仅参考”。
2. **先适配，再重写。** 已验证的安全/持久化/协议实现优先包一层适配，不轻易重写。
3. **先试点，再推广。** 用一个真实模块验证规则，规则被证伪就改规则，不要一次铺开。
4. **目录最后动。** 先把规则套到现有目录上跑通；物理重排是验证结果，不是施工前提。
5. **一次只保留一个真相。** 迁移过程中不允许 Rust 和 UI 同时维护同一业务状态。
6. **可回滚。** 每步都能回到上一步；不删旧代码直到新路径验证通过。
7. **验收不是“能编译”。** 是“新增功能局部完成 + 删除模块可编译 + 并行施工不冲突”。

## 2. 迁移步骤

### 步骤 0：资产盘点（1-2 周，最高优先）

产出：一张**资产 → 处置**矩阵，覆盖现有全部 crate、apps、contracts、docs、reference。

每个单元记录：

- 现状：职责、规模、测试、被谁依赖；
- 对应 WEXPC1 的哪个规则/模块；
- 处置：复用 / 适配 / 包裹 / 替换 / 仅参考 / 冲突待决；
- 证据：路径、测试、文档；
- 批次：P0/P1/P2。

主仓需要重点盘点的单元：

| 单元 | 为什么重要 |
|---|---|
| `crates/wex-core` | 同时含权限、Operation、Task、dispatch、lease、execution policy |
| `crates/wex-desktop-service` | domain / application / connectors / infrastructure 四层，连接器已在此 |
| `crates/wex-api` | 协议核，已有 decoder/encoder/errors/types 与测试 |
| `crates/wex-access-store` | 私有 ACL、原子替换、读会话，安全资产 |
| `crates/wex-local-resources` | 本地文件能力 + 平台适配 |
| `crates/wex-workspace-store` | 组织/任务/操作/agent dispatch 多域持久化 |
| `crates/wex-protocol` | 严格 JSON，但仍是 demo 操作 |
| `apps/desktop/src-tauri` | `tool_catalog` / `tool_approvals` / `vault` / `github_config` / `local_access` |
| `apps/desktop/src` | React 交互层与 `types.ts` / `client.ts` |
| `contracts/` | 已有类型提案与测试 |
| `bridge/`、`reference/` | 旧 FFI 与历史参考，必须与产品路径隔离 |

退出条件：

- 每个单元都有处置，没有“待定”超过 20%；
- 冲突项（同一职责多个 owner）被列出；
- 产出一份“双真相风险清单”。

### 步骤 1：规则校准（1 周）

把 WEXPC1 的规则与主仓现有基线对齐，而不是直接执行 WEXPC1。

对照主仓已有文档：

- `docs/architecture/WEXPC-LIGHTWEIGHT-HOST-ARCHITECTURE-V0.1.md`
- `docs/proposals/WEXPC-ARCHITECTURE-DEDUP-BASELINE-REVIEW-V0.6.md`
- `docs/INTERFACE-CONTRACTS.md`、`docs/PROJECT-CONSENSUS.md`
- `docs/PC-PRODUCT-AND-TECH-BASELINE.md`

每条 WEXPC1 规则分四类：

| 分类 | 处理 |
|---|---|
| 已被主仓覆盖 | 从 WEXPC1 删除或只留引用 |
| 补充主仓缺口 | 合并进主仓基线，WEXPC1 标记 promoted |
| 与主仓冲突 | 以主仓为准，或开 ADR 明确改哪边 |
| 不适用于当前阶段 | 标记候选/后置，不施工 |

退出条件：

- 没有“两套同时生效”的规则；
- 冲突项都有裁决（主仓为准 / ADR / 后置）。

### 步骤 2：适配与包裹（2-3 周）

在不推翻现有实现的前提下，把现有资产接到新规则上：

- 连接器：为 `wex-desktop-service/src/connectors/*` 补**能力声明**（side effect / approval / idempotency / evidence）；
- 凭证：`src-tauri/vault.rs` 作为 `secrets` 适配层，业务模块只拿引用；
- 审批：`src-tauri/tool_approvals.rs` 收敛为 policy 的执行点之一，不在 UI 另判；
- 能力目录：`src-tauri/tool_catalog.rs` 作为 registry 雏形，补 descriptor，而不是重建 registry；
- 操作/回执：复用已有不可变回执/检查点，补统一 ledger 接口；
- 存储：`wex-workspace-store` 与 `wex-desktop-service/infrastructure` 先保留，补 owner 声明，不急于拆。

退出条件：

- 至少一个连接器（GitHub 或本地文件）能通过统一 Invocation 走通；
- 操作记账与回执复用现有实现，而不是新写一套；
- 没有新增第二套状态。

### 步骤 3：窄试点（2-3 周）

选一个真实功能验证“局部性”，例如 GitHub Issue 或现有 `tool_catalog` 的能力声明化。

通过标准：

- 模块外改动 ≤2 个文件；
- `wex-core` / `wex-desktop-service` 的公共层零业务改动；
- 契约测试/回放测试通过；
- 不要求真实网络/凭证。

失败含义：规则或现有边界需要调整；不要继续铺开。

### 步骤 4：收公共机制（1-2 周）

在试点中观察到的重复，才上升为公共机制：

- 凭证存取；
- 操作账本/回执；
- 权限判定组合；
- 持久化/迁移框架；
- 事件/通知。

原则：**先有重复，再抽公共。** 不先造公共再找用途。

退出条件：

- 至少两个连接器使用同一机制；
- 机制里没有业务词；
- 删除任一连接器，机制仍能独立测试。

### 步骤 5：目录归位（最后，1-2 周）

只有在步骤 0-4 验证通过后，才考虑物理目录调整：

- 先调整**逻辑模块清单与 owner**，再调整目录；
- 一次只搬一个模块；
- 每次搬完跑完整测试 + 依赖检查；
- 不为了“目录好看”搬没有收益的模块。

如果现有 crate 已经能承载逻辑边界（主仓当前就是这种路线），**可以不搬**。目录不是目标，边界才是。

### 步骤 6：上护栏（持续）

- CI 接入 arch-check、契约测试、依赖图快照；
- PR 模板加“四问”；
- 每月统计：模块外改动数、契约变更数、跨模块 import 数、循环依赖数、双写字段数。

退出条件：

- 违规能在 CI 拦截，而不是靠评审记忆。

### 步骤 7：删旧路径

- 旧目录归档/删除；
- 旧协议/旧接口标记退役（`wex-protocol` 的 demo 操作是候选）；
- 数据迁移完成并验证；
- 文档权威更新（superseded 索引）。

退出条件：

- 仓库里没有两套实现；
- 新 AI 不会误读旧路径。

## 3. 旧代码处置策略

对每个旧 crate/文件，选一种处置：

| 处置 | 适用 | 做法 |
|---|---|---|
| 复用 | 纯领域规则、安全实现、协议核 | 直接保留/迁入对应模块，保留测试 |
| 适配 | 接口/存储/平台差异 | 包一层适配到新契约，不重写 |
| 包裹 | 现有实现暂时不想动 | 在外面加统一接口/声明，内部保持原样 |
| 替换 | demo/过期协议/临时实现 | 标记退役，新实现上线后删除 |
| 仅参考 | 历史 UI/实验代码/旧 FFI | 移到 `reference/`，不进入构建 |

**不要**因为“代码相似”就假定可复用；每个都要有测试证据。

## 4. 双真相风险与处理

迁移期最容易出现：

- Rust 和新模块都维护连接配置；
- UI 和新服务都维护组织/任务状态；
- 旧协议和新契约都对外暴露；
- `domain` 与 `application` 同名文件各存一份规则（例如 `execution_policy`、`task_records`、`member_brief`）。

处理：

1. 指定唯一权威（写入口）；
2. 旧路径只读或只转发；
3. 用开关切换，切换后旧路径失效；
4. 数据迁移脚本必须可重跑/可回滚；
5. 加“双写检测”测试：同时改两边，断言不一致会报错；
6. 同名文件先审计职责：是“领域规则 vs 应用服务”的合理分层，还是重复 owner。

## 5. 回滚策略

- 每步迁移在独立分支/开关后；
- 数据迁移前备份；
- 新路径验证通过前，旧路径保留；
- 出问题时回退开关，不靠回滚代码；
- 归档旧代码而不是立即删除，直到确认无引用。

## 6. 迁移完成的判断

不是“目录建好了”，而是：

- 新功能只在模块内完成；
- 删除模块后系统仍可构建（除组合根）；
- 两个 AI 并行改不同模块无冲突；
- 依赖图无违规边、无环；
- 契约有版本、有契约测试；
- 旧路径已删除/退役，文档权威已更新。

## 7. 迁移中的常见错误

1. **先搬目录后定规则**：目录搬完，写法没变，很快长回原样。
2. **在活跃主仓上“搭新骨架”**：重复建设，和现有实现抢真相。
3. **一次性重写**：风险高、无法验证、容易丢已验证行为。
4. **保留双实现“以防万一”**：永久双真相。
5. **为迁移方便在公共机制加业务**：污染机制。
6. **跳过试点直接铺开**：规则未验证，返工大。
7. **只迁移代码不迁移测试**：失去安全网。
8. **不设退出条件**：迁移变成长期状态。
